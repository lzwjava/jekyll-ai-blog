This file implements **prefill scheduling** for `mini-sglang` — the "process the prompt" phase of LLM inference, which must happen before token-by-token decode. It's a miniaturized version of SGLang's scheduler logic, centered on **chunked prefill**: long prompts are cut into chunks that fit the current token budget, and unfinished requests are resumed on later schedule rounds.

## The two classes

### 1. `ChunkedReq` (lines 24–30)
A `Req` subclass that disables sampling/decoding:

- `append_host` raises — a chunked request hasn't finished its prompt, so it must never be sampled.
- `can_decode` returns `False` — the decode manager's `filter_reqs` skips it, so a partially-prefilled request stays in the prefill pipeline.

### 2. `PrefillAdder` (lines 33–97) — admission control
The core logic: try to fit one pending request into the current budget.

**`_try_allocate_one`** (lines 41–59) reserves resources *before* committing:
1. Bail if the table manager (request slots) is full.
2. Query the cache manager for a **prefix match** (`match_req` → prefix caching: if part of the prompt is already in the KV cache, reuse it; `cached_len` is the number of cached tokens).
3. Estimate total tokens needed: `extend_len + output_len` (new tokens to prefill + tokens the response will consume), and check against available cache — **accounting for a `reserved_size`** (in-flight decode tokens, see below).
4. `lock` the cache handle, re-check (race-safety), and allocate a table slot.
5. If there's a cached prefix, copy the cached token IDs and the matched page-table entries into the new slot — this links the pre-existing KV pages to this request's page table.

**`_add_one_req`** (lines 63–84) performs the actual addition:
- Computes the chunk: `min(token_budget, remain_len)`. If the whole remaining prompt doesn't fit, it wraps the request in a `ChunkedReq`.
- Decrements the budget and **increments `reserved_size`** by the remaining prompt + output tokens, so subsequent requests in this batch don't overcommit.
- Copies only the chunk's token IDs into the token pool (pages are allocated later in the scheduler).
- Returns a `Req` with the partial prompt (`input_ids[:cached_len + chunk_size]`) and its resource handles.

**`try_add_one`** (lines 86–97) is the entry point with two paths:
- **Resume path:** if the pending request already has a `chunked_req`, skip allocation entirely — reuse its cache handle/table slot and just prefill the next chunk. This is what makes chunked prefill cheap to continue.
- **Fresh path:** allocate new resources, then add.

Returns `None` when out of budget — and since the pending list is FIFO-ordered, the caller treats `None` as "stop, no more fit."

### 3. `PrefillManager` (lines 100–141) — the scheduler

**`add_one_req`** — a new user request becomes a `PendingReq` (prompt tokens + sampling params) in the queue.

**`schedule_next_batch`** (lines 108–134) — builds the next prefill batch:
- Creates an `adder` whose `reserved_size` is seeded with `decode_manager.inflight_tokens` — i.e., tokens currently being generated by decode requests are treated as already-consumed cache, so prefill never steals pages from in-flight decodes. This is the key memory-coordination point between the two phases.
- Iterates the pending list, greedily adding requests until the budget is exhausted (`break` on `None`).
- Preserves ordering: `pending_list = chunked_list + self.pending_list[len(reqs):]` — resumable chunked requests stay at the front (they'll be scheduled first next round), followed by the requests that didn't fit.
- Returns a `Batch(phase="prefill")`, or `None` if nothing could be scheduled.

**`abort_req`** — removes a request from the queue and returns its in-progress `ChunkedReq` (so the caller can free its resources).

**`runnable`** — whether the queue is non-empty (used by the main scheduler loop to decide if a prefill step is needed).

## How it fits together

```
UserMsg → PrefillManager.add_one_req → PendingReq queue
              │
              └─ schedule_next_batch (prefill_budget tokens)
                   ├─ DecodeManager.inflight_tokens  → reserved cache (don't steal from decode)
                   ├─ CacheManager.match_req         → prefix-cache reuse
                   ├─ chunk if prompt > budget       → ChunkedReq, keep PendingReq at queue head
                   └─ Batch(phase="prefill") → scheduler allocates pages, runs the model
```

In short: this file is the **resource-admission and batching logic for the prefill phase** — it balances prompt processing against decode's cache needs, reuses cached prefixes, and transparently chunks long prompts across multiple schedule rounds.
