## 问题：在AI/氛围编码使代码行数和提交量成为糟糕衡量标准的当下，应该如何协商软件项目并准确估算成本？是否应该改用token来衡量？

## 答案：

**不要按LOC、提交量或token来为AI辅助软件定价。** 这些衡量的是*活动量*，而非*交付价值*。

基本的计价单位应该是：

> **成本 = 工程工作量 × 风险 × 所需质量 + 基础设施/第三方成本**

AI改变了生产函数：一名工程师可以生成10倍的代码。因此旧的`LOC → 工时 → 价格`模型已经失效。

### 1. 为什么LOC/提交量/token是糟糕的指标

| 指标 | 失效原因 |
|------|----------|
| LOC | AI可以在几秒内生成10,000行无用的代码 |
| 提交量 | 一次提交可以是10行或10,000行 |
| 生成的token | 严重依赖于模型、冗长程度、重试次数和上下文 |
| 消耗的token | 衡量的是AI使用量，而非商业价值 |
| 工时 | 稍好，但仍不能捕捉项目风险 |
| 交付的功能 | 好得多 |
| 验收标准 | **固定价格项目的最佳基础** |

例如：

```text
传统开发者：
  500行/天

AI辅助开发者：
  5,000行/天
```

如果你按LOC定价，就等于无意中制造了产生更多代码的激励。

相反：

```text
客户想要：
  API
  仪表盘
  认证
  支付
  部署
  监控

你为完成的系统定价。
```

## 2. 使用基于交付物的估算模型

在报价之前，先分解项目：

```text
项目
├── 需求
├── 架构
├── 后端
├── 前端
├── AI/LLM
├── 数据库
├── 集成
├── 部署
├── 测试
└── 维护
```

然后将每个部分转化为**验收标准**。

示例：

```text
认证

[ ] 邮箱/密码登录
[ ] 密码重置
[ ] JWT/会话管理
[ ] 速率限制
[ ] 管理员/用户角色
[ ] 20个自动化测试
[ ] 生产部署
```

现在协商变成了：

> "当这些标准得到满足时，这个里程碑就完成了。"

这比以下说法更难引起争论：

> "我写了30,000行代码。"

# 3. 内部估算工作量，对外销售成果

我会保留如下内部计算：

```python
estimate = {
    "requirements": 2,
    "architecture": 2,
    "backend": 5,
    "frontend": 4,
    "integration": 3,
    "testing": 3,
    "deployment": 2,
}

hours = sum(estimate.values()) * 8
```

假设：

```text
26 工程师天
```

然后考虑不确定性：

```text
26 × 1.3 = 34 工程师天
```

如果你的内部目标费率是：

```text
¥4,000/天
```

那么：

```text
34 × ¥4,000 = ¥136,000
```

你可能报价：

```text
项目：¥150,000
```

客户不需要看到：

```text
backend = 5 天
frontend = 4 天
...
```

除非你想协商范围。

# 4. AI让你的利润率变得更加重要

这是AI编码对你的业务变得极为有趣的地方。

假设历史上：

```text
客户价格：      ¥150k
人工工程：      30天
成本：          ¥90k
毛利润：        ¥60k
```

有了强大的AI工具：

```text
客户价格：      ¥150k

你的实际成本：
  人工：        12天
  API/模型成本： ¥3k
  基础设施：     ¥2k

总成本 ≈       ¥41k
毛利润 ≈       ¥109k
```

**你不应该自动将价格降到¥60k。**

客户购买的是：

> 一个具有责任归属的工作系统

而不是：

> 30天的打字时间。

这与高效的外科医生不会因为手术时间更短而收费更低是同一个道理。

# 5. token*确实*有用的地方

Token对你的**内部AI成本核算**很有用，尤其是当你正在构建一家AI原生软件公司时。

追踪：

```text
项目
├── 输入token
├── 输出token
├── 模型/API成本
├── 工具调用
├── Agent运行时间
├── 人工干预
├── 迭代次数
└── 基础设施
```

例如：

```text
项目A

Claude/Codex等：
    input：   80M tokens
    output：  12M tokens
    API成本： $420

Agent执行：
    1,800 次工具调用

人工：
    38 小时

基础设施：
    $90
```

这给你一个非常有用的指标：

```text
AI成本 / 项目
AI成本 / 已验收功能
AI成本 / 工程小时数
```

但是**不要告诉客户**：

> "这个项目消耗了80M token，所以成本是¥X。"

这等同于建筑公司按工人的击键次数收费。

# 6. 我为你公司实际构建的指标

既然你在做AI咨询/Agent开发，我会追踪**四个层级**：

```text
                    客户
                      │
                商业成果
                      │
                验收标准
                      │
              工程生产
                      │
        ┌──────────────┴──────────────┐
        │                             │
     人工工作                   AI生产
        │                             │
     小时                         token
     决策                         工具调用
     评审                         模型成本
        │                             │
        └──────────────┬──────────────┘
                      │
                 实际COGS
```

你的财务模型变为：

```text
收入
  ↓
项目价格
  ↓
- 人工
- 模型/API成本
- 云/GPU
- 软件
- 分包商
  ↓
毛利润
```

而你的生产力模型变为：

```text
交付价值
-------------------------
人工小时 + AI成本
```

这远比LOC/小时更有意义。

# 7. 对于固定价格项目，协商范围——而非小时

这可能是最重要的部分。

不好的方式：

> "我将用30个工程师天来开发这个。"

更好的方式：

> "¥150k包括A、B、C和生产部署。超出这些验收标准之外的任何内容都视为变更请求。"

然后定义：

```text
里程碑1 — ¥30k
需求 + 架构

里程碑2 — ¥50k
核心应用

里程碑3 — ¥40k
AI/集成

里程碑4 — ¥30k
生产 + 验收
```

并明确定义排除项：

```text
不包含：
- 新的第三方集成
- 重大UI重新设计
- 新的业务工作流程
- >N并发用户
- 额外语言
- 新AI模型
```

这可以防止**范围蔓延**，这通常比你最初的估算偏差20%要危险得多。

---

# 8. 何时使用按小时/按天定价更好

当不确定性高时，使用基于时间的计费：

```text
"为我构建一个自动化我们工作流程的AI Agent。"
```

你还不知道：

* API限制
* 数据质量
* 模型性能
* 集成复杂性
* 客户的实际工作流程
* 安全要求

那么首先销售一个**发现/原型阶段**：

```text
阶段0
¥20k–50k

1–2周

交付：
  架构
  原型
  基准测试
  技术风险
  详细实施估算
```

然后：

```text
发现
   ↓
已知需求
   ↓
固定价格实施
   ↓
维护
```

这对于AI项目尤其强大，因为不确定性通常集中在**首次实验**中。

## 我为AI原生咨询公司推荐的定价系统

我会使用：

```text
              发现
                  │
             固定价格
                  ↓
          原型 / 概念验证
                  │
             固定价格
                  ↓
        生产项目
                  │
         里程碑定价
                  ↓
            维护
                  │
         按月 / 顾问费
```

内部，收集**小时 + token + 工具调用 + 基础设施 + 缺陷 + 返工**。

外部，销售**范围 + 验收标准 + 商业成果 + SLA**。

因此关键区别在于：

```text
成本衡量：
    人工小时
    模型token/$
    基础设施
    返工

价值衡量：
    已验收功能
    商业成果
    可靠性
    性能
    SLA

范围衡量：
    验收标准
```

**因此，token是有用的，但作为COGS指标——而非定价单位。**

针对你的特定AI咨询业务，我还可以构建一个具体的**`project_estimator.py`**，它接收需求、风险、人工小时、模型token、GPU/API成本和目标利润率，输出报价和里程碑计划。
