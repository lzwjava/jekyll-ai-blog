**问题：** 这篇关于 Citadel 的论文（Jia, Maggioni, Staiger, Scarpazza 2018）讲了什么？为什么 Aleksa Gordic 在一篇关于矩阵乘法优化的博客文章中引用了它？

**回答：**

这是一份关于 V100（Volta）微架构的逆向工程报告——没有任何 NVIDIA 白皮书能提供如此详细的细节，因此作者通过微基准测试和 SASS 反汇编获得了这些信息。Gordic 引用它，是因为编写一个高效的 GEMM 内核（他博客的核心目的）恰好需要这篇论文揭示的内容：寄存器组布局、指令延迟以及张量核心的数据移动——这些内容均未公开文档化。

**1. 引人入胜的切入点：寄存器组冲突会损失真实的 GFLOPS 性能**

Volta 将其寄存器文件分为 2 个 bank，每个 bank 64 位，不同于 Pascal/Maxwell 上 4 个 bank 的 32 位设计。一条 FFMA 指令每个周期只能从每个 bank 读取 64 位，因此如果三个源寄存器落在同一个 bank 中，访问就会串行化。他们的示例是一个朴素的寄存器分块 8×8 外积 GEMM 内循环：

```cuda
__shared__ float shr_A[8*512], shr_B[8*512];
float reg_A[8], reg_B[8], reg_C[64];
for (int k=0; k<512; k++) {
  for (int i=0;i<8;i++){ reg_A[i]=shr_A[i+k*8]; reg_B[i]=shr_B[i+k*8]; }
  for (int i=0;i<8;i++)
    for (int j=0;j<8;j++)
      reg_C[i*8+j] += reg_A[i]*reg_B[j];
}
```

NVCC 9.0 生成的寄存器映射在此模式上存在 bank 冲突。手动修补 SASS 以消除冲突并利用寄存器重用缓存，将每个包含 128 个线程的 warp 的性能从 132.05 GFLOPS/SM 提升到了 152.43 GFLOPS/SM —— 仅通过寄存器分配就获得了 +15.4% 的提升。这正是整篇论文的论点："存在 cuBLAS 内部团队才知道的可免费获取的性能等待挖掘。"

**2. 内存层次结构——进行分块决策时真正需要的数值**

| 层级 | V100 (GV100) | 备注 |
|---|---|---|
| L1 数据 / 共享内存（统一） | 32–128 KiB，命中延迟 28 周期 | 相比之下 Pascal 为 82 周期——这是 Volta 的重大优势 |
| L2 | 6,144 KiB，约 193 周期，2155 GB/s | 16 路组相联，统一存储数据/指令/常量 |
| 全局内存 (HBM2) | 理论 900 GB/s，实测约 750 GB/s（效率 83.3%） | 他们测试过的所有代中效率最高 |
| 寄存器 | 2 个 bank × 64 位 | bank = reg_index % 2 |
| 共享内存 | 每个 SM 最多 96 KiB，无冲突延迟 19 周期 | 32 个 bank × 4B |

该论文使用指针追逐（p-chase）技术测量了全局内存访问延迟：L1 命中为 28 周期，L1 未命中/L2 命中为 193 周期，L2 未命中/TLB 命中为 375 周期，完全未命中（L2 和 TLB 均未命中）为 1029 周期。

**3. 他们实际如何进行微基准测试（方法，代码优先）**

他们的延迟测量技巧，可推广到任何没有文档的 GPU：

```
// 固定延迟指令 A：
// 用依赖指令 B 将其括起来，缩小 A 的“暂停周期”
// 控制字字段，直到 B 的结果变得错误。
// 最后一个正确的暂停计数 = A 的真实延迟。

// 可变延迟指令 A（加载、原子操作）：
// 与已知延迟的 B 配对，通过控制字障碍强制
// 人工读写依赖关系，
// 使用 CS2R（时钟到寄存器）指令对测量，
// 减去 B 的已知延迟。
```

大多数 Volta 整数/FP32 指令（IADD3、FFMA、FADD、ISETP...）延迟为 4 周期，而 Pascal 为 6 周期；DFMA/DADD 为 8 周期；半精度 HFMA2 为 6 周期——低于旧的 FMA 延迟 6 周期，这就是为什么 Volta 的调度器与核心比率很重要（从 Kepler 的 1:48 增加到 1:16，使得指令吞吐量能够随更短的延迟扩展）。

**4. 张量核心——这是与现代矩阵乘法工作最相关的部分**

一个 wmma::mma_sync 调用编译为 4 组 HMMA 指令，每组 4 条（共 16 条），对每个 warp 的 16×16×16 半精度 tile 进行操作。在运行时，32 个线程分成 8 组，每组 4 个（组 = thread_id/4），每组计算 16×16 输出的一个 4×8 块，不同的 HMMA 组贡献不同的累加步骤。这就是 `mma_sync` 内部实际的数据并行分解方式——没有 NVIDIA 文档会告诉你这些；这就是为什么人们编写 CUTLASS 而不是手工实现 WMMA。实测的张量核心吞吐量达到理论峰值的 90.2%，而 FP32/FP64 几乎可以达到 100%——论文自己的解释是它们在 图4.2–4.7 中描绘的寄存器加载和线程映射开销。

**为什么 Gordic 引用这篇论文：** 他的矩阵乘法博客可能是在讲解寄存器分块 / warp 分块 GEMM 内核（CUTLASS 风格的层次结构：块 tile → warp tile → 线程 tile → 指令）。这篇论文是解释 *为什么* 在 Volta 上这些 tile 大小和寄存器映射被如此选择的主要来源——bank 宽度、重用缓存、HMMA 组语义。对于任何想要从头构建 GEMM 而不是将 cuBLAS 视为黑盒的人来说，这基本上是“地面实况”引用。
