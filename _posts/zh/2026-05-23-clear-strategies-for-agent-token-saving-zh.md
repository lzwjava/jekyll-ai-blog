**问题：** 频繁使用 `/clear`（开启新会话）是否是在使用 Claude/Hermes 代理时节省 token 的策略之一？

**回答：**

是的，完全正确。在任何基于 CLI 的代理工作流中，`/clear` 是最直接的 token 节省手段之一。以下是背后的思维模型：

## 为什么上下文长度 = token 成本

会话中的每条消息都会追加到上下文窗口中，而该窗口会在**每次后续 API 调用**中被发送。因此，一个 50 轮对话的成本不是 50 ×（最后一条消息的 token 数），而是 50 ×（累积历史 token 数）。在实际使用中，这呈二次增长。

```
第 1 轮：发送 100 个 token
第 5 轮：发送 500 个 token
第 20 轮：发送 2000 个 token  ← 即使每条消息都很短
```

## `/clear` 作为手术刀

当你执行 `/clear` 时：
- 上下文重置为零（或仅保留系统提示）
- 下一次调用只消耗新消息 + 系统提示的 token
- 你会丢失历史记录，但获得一个干净的起点

关键在于：**大多数任务并不需要完整的历史记录**——它们只需要最近 1-3 轮的上下文。因此，在不同子任务之间使用 `/clear` 几乎总是正确的选择。

## 何时积极使用 `/clear`

| 场景 | 清除？ |
|---|---|
| 从调试切换到编写代码 | ✅ 是 |
| 新文件 / 新功能 | ✅ 是 |
| 经过长时间的多工具探索后 | ✅ 是 |
| 在调试单个 bug 的过程中 | ❌ 否——上下文至关重要 |
| 继续执行多步骤计划 | ❌ 否 |

## 与 `/clear` 搭配使用的其他 token 节省策略

由于你正在构建 CLI 代理（`ww`、`zz` 等），你可能已经知道其中一些，但完整的图景如下：

1. **频繁使用 `/clear`**——主要手段
2. **精简系统提示**——不要在每次会话中塞入 2000 个 token 的指令
3. **工具输出截断**——如果代理读取文件/运行 bash，在注入上下文之前主动截断标准输出
4. **先总结再清除**——让 Claude 总结当前状态 → `/clear` → 将摘要作为第一条消息注入。有损但成本低
5. **任务分解**——将大型代理任务拆分为独立的子任务，每个子任务使用全新的会话
6. **避免重新读取未更改的文件**——在客户端缓存文件内容，不要每轮都重新注入

## 代码中的“先总结再清除”模式

```python
def compress_session(client, history):
    summary = client.messages.create(
        model="claude-sonnet-4-20250514",
        max_tokens=500,
        messages=history + [{
            "role": "user",
            "content": "用 <200 词总结当前任务状态。包括：已完成的内容、接下来要做的事、任何关键变量/路径/决策。"
        }]
    )
    # 现在清除历史记录，仅注入摘要
    return [{
        "role": "user", 
        "content": f"[会话恢复] 上下文：{summary.content[0].text}"
    }]
```

这就是 Claude Code 中“compact”（压缩）功能的内部实现——本质上就是一次总结加清除。

## 总结

是的，`/clear` 是一级策略。需要养成的思维习惯是：**将每次 `/clear` 视为一个 git 提交边界**——完成一个连贯的工作单元，清除，重新开始。不要仅仅因为方便就让上下文在不相关的任务中累积。
