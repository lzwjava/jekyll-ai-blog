## 三大重要洞察

### 1. 连续批处理 ≠ 静态批处理

**静态批处理**（简单方法）：
- 等到有 N 个请求
- 将所有提示填充到相同长度
- 对所有序列运行所有 max_tokens 步骤
- 一个简短问答要等 64 步直到文章完成

**连续批处理**（vLLM 的做法）：
- 每个序列独立推进
- 短的序列完成并 **立即离开**
- 新的序列可以 **中途加入**
- 批处理大小每步都在变化

### 2. "free_blocks" 揭示了内存的故事

```
free_blocks:  6 → 1 → 7 → 11 → 14 → 16 → 23
```
- 从 6 开始（部分块被模型权重占用）
- 在峰值压力下降至 1（所有 10 个序列活跃）
- 随着序列完成并释放其 KV cache 块，**攀升至 23**
- 这是 PagedAttention 的块级内存管理实际运行

### 3. prompt_len 与 total_len

看 seq[11]：
```
prompt_len=187  total_len=219  blocks=1
```

它有 **187 个提示 token + 32 个生成 = 219 总计**，但只有 **1 个块**。为什么？因为块大小是 256 个 token。一个 256 token 的块就能容纳其所有 KV cache。这就是 PagedAttention 中的 **page**。

## 如果没有 vLLM 会发生什么？

没有连续批处理 + PagedAttention：

1. **内存浪费：** 你会为所有 10 个序列分配 KV cache 用于 `max(64, 48, 32, ...)` = 64 步。短序列浪费了 60 步的缓存。
2. **无抢占：** 如果内存耗尽，系统会崩溃。
3. **碎片化：** 顺序分配会在序列在不同时间完成时产生空洞。

使用 PagedAttention：
- 块按需分配
- 当 seq[6] 完成时，其块回到空闲池
- seq[7]（文章）可以使用该块进行下一个 token
- **零碎片，零浪费**

## 总结性的一句话

你正在观察 **transformer 的虚拟内存**——PagedAttention 之于 GPU 内存，就像虚拟内存分页之于 CPU 内存。每个序列都有一个逻辑的“页表”（block_table），将其 token 映射到物理 GPU 内存块。调度器就是操作系统，随着序列的进出而分配和释放页面。

这就是为什么 vLLM 能够比简单实现多服务 10 倍并发用户的原因。
