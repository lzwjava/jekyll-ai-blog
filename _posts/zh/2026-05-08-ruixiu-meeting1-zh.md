## 2. 为什么“底层算法”和“开发产品”是两条不同路径

关于方向，资深程序员首先分享了对另一个学生（阳阳）的观察：那个学生研究的是 **NVIDIA 栈内的优化**（显存、内存移动、内核级工程）。这种工作本质上属于运维和工程——有时也能带来关键发现，比如 FlashAttention。

这位高中生的立场很明确：

- 他更喜欢深入挖掘和思考**算法层面的创新**；
- 比如研究注意力机制、研究 RoPE（他提到了苏剑林关于“旋转”注意力的工作），并思考如果“把某个注意力偏转90度”会发生什么；
- 至于“你最终只会做产品”的说法，他不同意——做产品是另一条路线，旨在将 AI 应用于生活的各个领域，而他想再往下走一步，更接近模型本身。

资深程序员的看法：**两条路都成立，但你必须清楚地知道自己走的是哪一条。**

然后他说了一些相当直白的话——大意是：在中国环境里长大，已经需要投入大量精力，但天外有天。与硅谷最顶尖的16岁少年相比，差距主要体现在两个地方：

1. **实际的英语表达能力**——极其熟练，像中文一样流利；
2. 计算机技能大致相当，但在 OpenAI 那种高强度沟通环境中，如果你的英语理解效率不如中文，那么解释“非常复杂的 transformer 讨论”时就会慢一步——仅此一点就可能让另一个候选人超过你，哪怕他思维并不更敏锐，AI基础也不更扎实。**沟通本身就是一项硬指标。**

所以他一直强调：**英语流利不关乎英语本身——而是关乎你未来不吃亏。**

## 3. Tree of Thoughts 项目：完整代码讲解

会议的技术核心是这位高中生分享他自己搭建的 **Tree of Thoughts** 物理问题解答系统。他在本地运行，并一步步讲解了架构。

### 3.1 模型分工：四种角色

该系统由四种模型协作：

| 角色 | 大小 | 职责 |
|------|------|------|
| **规划模型（协调器）** | 大（120B） | 将问题分解为元任务→任务，逐步规划 |
| **建模模型** | 中（9B） | 严格遵循规划器的指令，**从不看到完整问题** |
| **审查模型** | 小（0.5B / 4B） | 检查每一步的逻辑，决定加噪/退回/通过 |
| **评估模型** | 小 | 主观评分，例如最终公式是否足够简洁 |

高中生解释了一个关键设计决策：**为什么建模模型不能看到完整问题？**

> 如果让它看到原始问题加上分解后的子任务，它会忍不住——试图“一次性解决整个问题”，而不是遵循分解。所以必须只给它当前步骤的指令。

资深程序员点评：“完全正确——你必须给它精确的东西，去掉所有不需要的，否则它会误解你的意思。”

### 3.2 为什么用 FSM（有限状态机）而不是简单数据结构

审查采用基于 FSM 的状态管理方法。高中生的理由：

- 节点不仅存储“算出了什么数值”——它还存储**边界条件、参数、被调用的技能以及这个建模步骤的约束**；
- 在求解物理问题时，每个中间答案都有适用范围，FSM 就是载体，将适用范围与答案一起存储；
- 这也是他后来放弃 DAG（有向无环图）合并思路的原因——不同分支几乎从不共享相同的前提假设（例如一个分支假设理想流体，另一个分支加了大量修正项）；即使两者计算出了相同的数值，也不能合并。

### 3.3 关于“发散”与“收敛”

他鼓励模型在最开始的节点**尽可能发散**，比如生成5-7种不同方法；后续如果某个分支只是添加一个修正项（如阻力），则无需进一步发散——审查模型会自行判断。

人文学科问题可能呈现相反的形状：在反驳某个现有观点的阶段，你可能反而需要在后期更多发散。**所以“思维树”的形状本身反映了学科的特性。**

### 3.4 技能系统与外部 SQL

他将所有“领域知识”外部化：

- 流体力学公式、功能关系公式等——**模型不被允许记忆这些**，它们被写入技能中；
- 模型只负责调用，不允许自己计算；
- 这避免了模型在没有规则约束的地方“胡乱猜测”。

### 3.5 协调器的局限与为什么先用小模型

演示产生的最终答案并不特别准确（例如某个问题给出了类似 `v_eff × h` 的形式，不够精确）。他坦率承认：

> “开源小模型还太弱了。如果我调用 API，结果肯定会好得多。”

但他强调了一种工作方法，资深程序员非常赞同：

> **首先，让整个流程在本地小模型上跑通，而不是直接跳到 API。**
>
> 小模型会暴露出你在调用 API 时永远不会看到的那些小坑；一旦整个流水线跑通了，换成更大的模型只会更好，不会更差。

## 4. 代码组织与 Codex / Copilot 习惯

他们一起浏览了几个文件：`backend / scheduler / models / planning_model / utils`。一些观察：

- 项目中某些模块（如 `merge`）是 AI 生成的，但目前未使用——他选择保留，理由是“可能对其他学科有用，物理中几乎没用”；
- 这位高中生使用 **Codex（更高级的 Copilot 层级，$140 计划）**，搭配 GPT-5.4 和高强度任务；运行整个项目只消耗了大约 7% 多的配额；
- 他授予 Codex **自动批准权限**，这样每个命令都不需要确认。他的判断：模型本身不会做有害的事，放弃这种控制权能显著提高效率；
- 他对 Codex 的使用更接近“协作”——让它来回运行测试并自行迭代——而不是把它当作一次性问答工具。

资深程序员的工具建议：

- 终端试试 **Ghostty**；
- 将 VSCode 中的每个界面都切换到英文；长期暴露在英文界面下是刻意的训练；
- 提问时，**尽量附上代码**——仅靠描述往往不准确；
- 对于较新的依赖项，直接将代码克隆到本地，通过类似 Cloud Code 的方式对着真实源码提问——这比让模型去网页搜索准确得多。

## 5. Mini-LLM 项目：类似 nanoGPT 的训练实现

接下来他们看了第二个项目——一个基于 nanoGPT 的 mini-LM 训练实现。

### 5.1 多版本与硬件适配

仓库中有多个版本的原因：他在不同的硬件上运行了同一份代码：

- MacBook（Flash Attention 不可用）；
- 他自己的 3090；
- 一个同学的 5090；
- 云上的 A100 和 A800。

不同硬件需要不同的精度、批大小和并行策略；他保留的是 A100 版本。

### 5.2 几个当场提问的细节

资深程序员像提问一样过了一遍 Transformer 细节：

- **RoPE（旋转位置编码）**：将位置变为可旋转的向量，使每个 token 之间更好地交互；在自回归情况下，使用正弦/余弦进行位置编码，注册为不参与参数更新的 buffer，并与模型一起保存；
- **KQV**：K 是这个 token“要找的东西”；Q 是 token 自身的信息；V 是这个 token 能为 token 间关系贡献的；
- **Flash Attention / mask**：他没有手动编写掩码，因为 PyTorch 内部已经处理了很多；
- **Transformer Block**：每侧一个 LayerNorm + 残差连接，中间是自注意力和前馈网络；
- **训练循环**：Adam 优化器、loss 反向传播、梯度更新、梯度清零——这三行代码在一起。资深程序员的看法：即使你通常不自己写优化器，理解这三行代码的语义对于调参或调试也至关重要。

### 5.3 数据规模与硬件升级

- 高中生的训练数据大约十几 GB；资深程序员用过 60GB；
- 他根据 token 数量反推参数上限，在刚过一半的地方停止训练；
- 他刚刚下单购买了 **NVIDIA Pro 6000** 来替换 3090（理由：3090 训练时太受限，Blackwell 优化还不够好，但显存大小是硬性需求）；他父亲在帮忙组装；
- 他的下一个目标：**原生多模态模型**。

## 6. 第三个项目：一个代理式编码实验

这是高中生搭建的一个小型“多智能体协作编码”系统，受 Cloud Code 启发：

- 使用 ddgs（DuckDuckGo Search）进行网页检索；
- 协调器**将大任务拆分成多个编码器子任务**（注意：这与 Tree of Thoughts 中“我只思考第一步”的方法相反——这里直接细分）；
- 每个编码器完成后，审查者首先进行静态检查（例如捕获低级错误，如 C++ 缺少分号）；如果有问题，**退回重写**（因为小模型越改越差）；
- 通过审查后，放入沙箱运行；
- 沙箱错误返回给协调器；多次尝试仍未成功后，协调器会**修改对应编码器的系统提示词**，使其不再犯同样的错误——他称之为“受控的 CSM 进化”。

他认为这个项目是一次性探索，没有继续维护，但确实通过它跑通了诸如“贪吃蛇游戏代码”这样的小任务。

## 7. 关于“证明你的水平”——来自资深程序员的重要建议

当话题转向 RoPE 和 KQV 时，资深程序员问了一个有点尖锐的问题：

> “你说你比那个邓明扬或 Kimi 的人强，但我其实有点怀疑。”

他进一步解释：这并不代表他怀疑潜力；关键是**局外人没有可靠的方式来评判这一点**。要让别人相信你比某个 0xy / IOI 奖牌得主强，通常有几种路径：

1. 与**已经比较了解你的人进行多次对话**，让他们在多个时间点看到你对 LM 知识的掌握程度；
2. 让简历自己说话——一眼看过去，读者就知道这个人比 X 强；
3. 在面试中被**足够资深的面试官当场认可**（他举了自己那天早上为渣打银行海外职位面试的例子——半小时后，面试官示意他通过了）。

说这些不是为了打击人，而是提醒：“你的水平”不能只是一种自我感觉。**它需要一个别人能看到的载体。**

他还谈到了一个有趣的点——**名字本身可以成为一种品牌**：

> “当人们听到你的名字就立刻知道你是顶尖人物时，你就完全成功了——你的名字就成了你的品牌。”

## 8. 关于“逆转近视”——资深程序员的一个边缘研究课题

会议中途，资深程序员分享了一个他多年从事的非主流话题——**近视的可逆性**。简要要点：

- 核心机制：佩戴比当前度数低100-150度的眼镜，使眼睛始终处于“需要轻微自我调节”的状态，慢慢调整眼轴长度；
- 做法：上课或看远处时戴足度数；日常近距离工作时戴低100度的眼镜；来回切换；
- 眼镜推荐：拼多多上三十到五十元的就行；
- 他追踪了三年：近视下降50度，散光下降75-100度，中间有反弹，但总体呈下降趋势；
- 推荐资源：**Todd Becker** 的网站和 **endmyopia** 社区。

他做了一个类比：这本质上与他理解 GPT 的方式相同——

> “2017年讨论 Transformer 的人也不多；真正有效的东西，在早期阶段只有少数人知道。”

他还提醒高中生，作为每天大量近距离用眼的人，这比项目工作更值得花几分钟关注。

## 11. 快速数学小测验

会议中还穿插了一次简短的小测验：

- **SVD（奇异值分解）**：将矩阵分解为 U Σ Vᵀ；
- **特征值分解**与 SVD 的关系；
- 矩阵乘法的“语义”：一种**信息交换**；
- 一个结论：**“人工智能中没有智能，也没有神经元；真正起作用的是微积分。”** 高中生补充：在 LLM 层面多了一层随机性，但底层的数学骨架确实如此；
- 在他看来，训练本质上就是“猜高或猜低”：猜低了梯度就往上推，猜高了梯度就往下推——不断迭代。

## 12. AI 工具与开发习惯总结

一些零散但有价值的点：

- **OpenRouter**：确实有用——可以横向比较“市面上最好的模型”在你具体问题上的表现；
- **One-shot / Few-shot**：模型输入 = 模型 = 输出；给一个例子就能显著提高准确率；
- **Cloud Code 的技能 / “Lobster”**（可能是听错的名字，可能叫 Lobster 或其他扩展）：高中生用得不多；
- **Hermes**：也很少使用；
- **iCloud + 自制小工具**：资深程序员写了一个粗糙但可用的 PDF 高亮工具——通过这个，他强化了“**搭建一个最小版本自然就让你了解了全貌**”的方法论。

## 结束语

这次对话涵盖范围很广：从一个16岁少年的 Tree-of-Thoughts 物理推理框架，到 RoPE 和 KQV 的现场提问，再到硅谷创始人的轶事、近视逆转以及“独立思考”的方法论。

如果要用一句话压缩，大概是这样的：

> **能力本身是必要的；但除了能力，你还需要一个让别人能看到它的载体——简历、项目、名字、英语流利度，以及别人在多次会面中形成的稳定判断。**

在技术层面，双方都认同：**先在小模型上跑通流程，再切换到大模型；让模型在你设计的边界内执行，而不是让它替你做思考。** 无论是搭建 Tree of Thoughts 还是 mini-LLM，根本上都是同一回事。
