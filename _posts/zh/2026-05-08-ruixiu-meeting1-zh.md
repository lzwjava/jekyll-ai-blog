## 3. 思维树项目：完整的代码走查

会议的技术核心是张睿修分享他自己的**思维树**物理问题求解系统。他在本地运行了该系统，并一步步地讲解了其架构。

### 3.1 模型分工：四个角色

该系统由四种模型协作完成：

| 角色 | 大小 | 职责 |
|------|------|------|
| **规划模型（编排器）** | 大 (120B) | 将问题分解为元任务 → 任务，逐步规划 |
| **建模模型** | 中 (9B) | 严格遵守规划器的指令，**绝不向其展示完整问题** |
| **审查模型** | 小 (0.5B / 4B) | 检查每一步的逻辑，决定是加入噪声、退回还是通过 |
| **评估模型** | 小 | 主观评分，例如最终公式是否足够简洁 |

睿修解释了一个关键的设计决策：**为什么建模模型一定不能看到完整问题？**

> 如果你让它看到原始问题加上分解后的子任务，它会忍不住——它会试图“一口气解决整个问题”，而不是遵循分解。所以，你只能给它当前步骤的指令。

资深程序员的评论：“完全正确——你必须给它精确的东西，去掉它不需要的一切，否则它会误解你的意思。”

### 3.2 为什么用 FSM（有限状态机）而不是简单的数据结构

审查环节使用了基于 FSM 的状态管理方法。睿修的理由是：

- 节点不仅存储“计算出了什么数值”——它还存储**边界条件、参数、调用的技能以及本次建模步骤的约束**；
- 在解决物理问题时，每一个中间答案都有其适用范围，FSM 就是将这些适用范围与答案一同存储的载体；
- 这也是为什么他后来放弃了 DAG（有向无环图）合并的想法——不同的分支几乎从不共享相同的前提假设（例如，一个分支假设理想流体，另一个分支则添加了一堆修正项）；即使两者计算出相同的数值，也不能合并。

### 3.3 关于“发散”与“收敛”

他鼓励模型在**最开始的节点尽可能发散**，例如生成 5-7 种不同的方法；之后，如果某个分支只是添加一个修正项（例如阻力），就没有必要进一步发散了——审查模型会自行判断。

人文学科的问题可能形状相反：在反驳已有论点的阶段，你可能实际上需要在后期更多地发散。**所以，“思维树”的形状本身就反映了学科的特性。**

### 3.4 技能系统与外部 SQL

他将所有“领域知识”外部化：

- 流体力学公式、功能关系公式等——**不允许模型记忆它们**，而是写入技能库；
- 模型仅负责调用，不允许自行计算；
- 这避免了模型在没有基于规则的约束的情况下“胡乱猜测”。

### 3.5 编排器的局限性以及为何从小模型开始

演示产生的最终答案不太准确（例如，一个问题最终得到类似 `v_eff × h` 的形式，不够精确）。他坦率地承认：

> “开源的小模型还是太弱了。如果我调用 API，结果肯定会好得多。”

但他强调了一种工作方法，得到了资深程序员的高度认可：

> **首先，让整个流程在本地小模型上跑通，而不是直接跳到使用 API。**
>
> 小模型会暴露出你调用 API 时永远看不到的那些小坑；一旦整个流水线跑通了，再切换到更大的模型，只会变得更好，不会更差。

## 5. 小型 LLM 项目：类似 nanoGPT 的训练实现

接下来他们查看了第二个项目——一个模仿 nanoGPT 的小型 LM 训练实现。

### 5.1 多个版本与硬件适配

仓库中有几个版本的原因：他在不同的硬件上运行了相同的代码：

- MacBook（无法使用 Flash Attention）；
- 他自己的 3090；
- 同学的 5090；
- 云端的 A100 和 A800。

不同的硬件需要不同的精度、批次大小和并行策略；他保留的是 A100 的版本。

### 5.2 现场测验的几个细节

资深程序员以问答形式快速考察了 Transformer 的细节：

- **RoPE (旋转位置编码)**：将位置变为一个可旋转的向量，使得每个 token 能更好地与其他 token 交互；在自回归情况下，使用正弦/余弦进行位置编码，注册为不参与参数更新且会一并保存的缓冲区（buffer）；
- **KQV**： K 是这个 token “在寻找的”东西； Q 是这个 token 自身的信息； V 是这个 token 能为 token 间关系贡献的信息；
- **Flash Attention / mask**：他没有手动编写 mask，因为 PyTorch 内部已经处理了很多这类工作；
- **Transformer Block**：两侧各有一个 LayerNorm + 残差连接，中间是自注意力和前馈网络；
- **训练循环**：Adam 优化器、loss backward、梯度更新、zero-grad——总共三行代码。资深程序员的看法：即使你通常不自己编写优化器，理解这三行代码的语义对于调整超参数或调试也至关重要。

### 5.3 数据规模与硬件升级

- 睿修的训练数据大约有十几 GB；资深程序员曾用到 60GB；
- 他从 token 数量反推参数上限，恰好停在超出该上限一半的位置；
- 他刚刚下单购买了 **NVIDIA Pro 6000** 来替换 3090（理由是：3090 对于训练来说太受限了，Blackwell 优化还不够好，但显存大小是硬性需求）；他父亲正在帮忙组装；
- 他接下来的目标是：一个**原生多模态模型**。

## 6. 第三个项目：一个智能体编码实验

这是睿修构建的一个小型“多智能体协作编码”系统，灵感来自 Cloud Code：

- 使用 ddgs（DuckDuckGo 搜索）进行网络检索；

- 每个编码器完成后，由审查者首先进行静态检查（例如，捕获低级错误，如 C++ 中缺少分号）；如果有问题，则将其退回**进行重写**（因为小模型越编辑越糟糕）；
- 通过审查后，将其投入沙箱运行；
- 沙箱错误返回给编排器；经过几轮尝试未成功后，编排器会**修改相应编码器的系统提示**，使其不再犯同样的错误——他称之为“受控的 CSM 演化”。

他评价这个项目是一次性探索，没有再继续维护，但他确实通过它完成了一些小任务，比如“贪吃蛇游戏代码”。

如果要浓缩成一句话，那大概就是：

> **能力本身是必需的；但除此之外，你需要一个让别人能看到它的载体——一份简历、一个项目、一个名字、流利的英语，以及他人在多次会面中对你形成的稳定评判。**

在技术层面，双方都同意：**先让小模型跑通整个流水线，然后再切换到更大的模型；让模型在你设计的边界内执行，而不是让它替你思考。** 无论是构建思维树还是小型 LLM，本质上都是同一回事。
