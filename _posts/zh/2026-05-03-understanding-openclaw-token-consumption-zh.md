**问题：**
为什么即使我没有主动使用 OpenClaw（根据 OpenRouter 的观察），它每天仍会消耗约 300 万个令牌？

**回答：**

简而言之：这几乎可以肯定是因为它*仍在后台进行工作*。

当像 OpenClaw（或类似的代理型框架）这样的系统运行时，从你的角度看“什么都没做”并不意味着系统处于闲置状态。这类系统通常构建为**持续循环**或**自主代理**，并且可能通过以下机制静默地消耗令牌：

---

### 1. 持续的代理循环（最常见原因）

许多代理框架都运行类似这样的逻辑：

```
while True:
    observe()
    think()
    act()
```

即使没有进行有意义的任务处理，模型仍在：

* 重新评估状态
* 生成思考或计划
* 重复调用 LLM

每次循环 = 令牌消耗。

如果循环运行速度很快（例如每 1–5 秒一次），你很容易就会达到每天数百万个令牌的消耗。

---

### 2. 隐藏的后台任务

OpenClaw 类型的系统通常包括：

* 记忆汇总
* 日志分析
* 环境轮询（如 GUI、浏览器等）
* 失败任务的重试循环

这些都可能触发 LLM 调用，例如：

* “总结当前状态”
* “决定下一步动作”
* “检查任务是否完成”

即使没有发生变化，模型仍会被查询。

---

### 3. 长上下文累积

如果系统持续追加历史记录：

* 每次新的调用都会包含**先前的消息**
* 令牌使用量会随时间增长

示例：

* 1k 令牌 → 2k → 4k → 8k 每次调用
  即使只有几次调用，每天的令牌消耗量也会变得非常庞大

---

### 4. 多个并行代理或线程

某些框架会静默运行：

* 规划器代理
* 执行器代理
* 评估器代理

因此，一个“步骤”实际上可能涉及**3–5 次 LLM 调用**。

---

### 5. 重试 / 失败循环

如果某些地方出现了轻微故障：

* API 调用失败
* 操作未完成

系统可能会无限重试：

```
尝试 → 失败 → 反思 → 重试 → 失败 → 反思 ...
```

这会迅速导致令牌消耗激增。

---

### 6. OpenRouter 的统计使其可见化

像 OpenRouter 这样的平台会显示**总的令牌使用量**，因此你会突然注意到：

* 后台循环
* 效率低下
* 失控的代理

如果没有这种可见性，你可能永远不会意识到这种情况正在发生。

---

### 大致估算

300 万个令牌/天 ≈

* 持续每秒约 35 个令牌，或
* 每次调用约 1,500 个令牌 × 每天 2,000 次调用

这与快速循环 + 中等规模的上下文完全吻合。

---

### 立即检查的项目

1. **进程是否仍在运行？**

   * 后台脚本 / 服务器 / Docker 容器？

2. **循环频率**

   * 查找 `while True` 或轮询间隔

3. **上下文大小**

   * 你是否在每次调用时都追加了完整的历史记录？

4. **每个步骤中的 LLM 调用次数**

   * 规划器 + 执行器 + 评判器？

5. **重试逻辑**

   * 是否存在无限重试循环？

6. **日志**

   * 即使闲置时，你也很可能会看到持续的 LLM 请求记录

---

### 实用的修复方法

* 添加**休眠间隔**（例如 5–30 秒）
* 当没有任务存在时停止循环
* 限制上下文长度（截断历史记录）
* 禁用未使用的代理
* 设置**每日硬性令牌预算**
* 记录每次 LLM 调用（你可以立即找到问题所在）

---

### 关键洞察

代理系统与普通应用程序不同。
如果你没有明确**停止它们**，它们的行为就像：

> “总是在思考，即使没有什么可思考的。”

而思考 = 令牌 = 金钱。
