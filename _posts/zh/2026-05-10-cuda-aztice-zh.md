## Axono 项目：一个用 CUDA 实现的极简 PyTorch 风格库

### 项目概览与动机

讨论开始于一位参与者介绍一个名为 [Axono](https://github.com/AxonoOfficial/Axono) 的项目，该项目托管于一个 GitHub 组织。开发者描述它是一个轻量级推理库，支持多种数据精度类型，包括 int8、int16、int32、int64、float32 和 float64。该库包含常用算子：矩阵乘法（matmul）、加法以及简单的激活函数。当被问及它是否像 PyTorch 一样是 Python 库时，开发者确认了这一点，但强调由于只有一个人开发，进展相当缓慢，令人疲惫。

该库主要针对 Linux 设计，虽然演示用的机器上存在 Windows 版本，但并未提供官方的 Windows 打包。开发者指出，当前展示的版本是 1.0，但澄清说演示的并非最新的 1.0 版本——而是一个较旧的发布版本。当被问及发布了多少个版本时，答案是大约十几个到二十个左右。开发环境是一台配备 NVIDIA V100 GPU 的机器。

### 当前状态与 V2 重构

对话转向了项目的结构。开发者解释说，当前的代码库（约几千行）相当混乱，这促使他们决定为 V2 版本进行完全重写。V0 版本存在严重的计时问题，因此 V1 版本从零开始开发以取代它。然而，V1 尚未完成，因为整个过程相当麻烦。一个关键的架构变化是，V1 将不再支持纯 CUDA——它将强制使用 CUBLAS。不过开发者提到，最终可能会为仍需要纯 CUDA 的老旧设备提供兼容性。

小组讨论了一个问题：Axono 能否用来编写一个像 MNIST 数字分类器这样的小型神经网络。该库目前不支持 Linear 层——这是构建此类模型的关键需求。开发者承认了这一限制，但指出由于 Axono 具有矩阵乘法功能，理论上可以使用数组来表示 Linear 层。大家一致认为这将是一个有趣的实验，一位参与者提到会拿代码去看看，尽管缺少 Linear 抽象，是否仍能实现一个极简的 MNIST 实现。

### 张量操作与形状处理

一位参与者演示了如何声明一个张量变量并查看其形状。在矩阵乘法的演示中，他们举了一个例子：矩阵 A 的形状为 (2, 3)，矩阵 B 的形状为 (3, 2)，并指出结果形状应为 (2, 2)。对于广播与标准矩阵乘法之间存在一些混淆——开发者澄清说，该库不会直接融合形状；而是将内部维度相乘，并将外部维度作为结果形状。

关于形状变换，开发者表示目前只提供了转置方法。没有通用的 reshape 或形状变更方法。转置实现只是简单地交换行和列（A[i][j] 变为 A[j][i]），但相关代码相对较长。当被问及高维张量时，该库仅支持二维转置——不支持同时转置多个维度。开发者指出，惯例是明确传递两个维度（dim0 和 dim1）。

### CUDA 实现：从 CPU 到 GPU 再返回

#### 内核启动流程

开发者从矩阵乘法开始解释了底层的 CUDA 实现。该过程首先分配内存，设置启动配置，然后调用内核。在内核内部，一个简化的循环遍历行和列，计算结果。该库包含优化：一个名为 `matmul_optimized` 的内核采用了列分块方法，旨在使整体计算更快。

为了优化性能，开发者使用了块大小和共享内存。具体来说，他们将块大小参数移入临时模板，将数据拉入共享内存块以加速矩阵乘法。分块的概念是将每个矩阵拆分为小块（tiles），以实现更高效的计算——类似于 Flash Attention 中使用的分块技术。

#### 共享内存与内核结构

一位参与者要求解释一下上下文中的共享内存。开发者坦言没有完美的直观解释，将其描述为一种将矩阵块加载到共享内存（GPU 上更快的存储空间）中的技术，以加速重复访问。代码中还包含边界检查，以确保索引保持在源张量和目标张量的边界内。对于转置操作，`idx` 变量用于计算源张量和目标张量中的位置。

矩阵乘法代码的跟踪显示，该库在启动内核前会检查张量形状的兼容性。`calculate_launch_config` 函数计算网格大小和块大小。块大小设置为 256。网格大小公式采用“向上取整”方法：`(num_elements + block_size - 1) / block_size`。一位参与者最初对这个公式提出疑问，想知道为什么 `num_elements` 不直接除以 `block_size`。开发者解释说，`+ block_size - 1` 的技巧确保了整数除法向上取整——当元素数量不能被整除时，这个公式会向上取整以分配足够的块。这是竞赛编程（OI）和通用 GPU 内核设计中的常见技巧。

#### CPU 与 GPU 之间的内存传输

讨论深入到了数据如何在 CPU 和 GPU 之间移动。开发者描述说，在内核执行期间，数据被“扔进”内核——这就是传输过程。当被问及哪个库负责这个传输时，开发者说是他们自己的自定义包装器。然而，他们澄清说，数据实际上并非在内核启动时从 CPU 移动到 GPU；张量从一开始就在 GPU 上初始化和分配。传递给内核的只是指向 GPU 内存的指针。然后内核直接在该 GPU 驻留数据上进行操作。

开发者打了个比方：CPU 使用指针调用 GPU 函数，GPU 内核通过提供的指针访问该内存。他们强调，GPU 和 CPU 是独立运行的——CPU 不能直接访问 GPU 内存，因此 CUDA（或 CUBLAS）提供了调用 GPU 函数的机制。GPU 计算完成后，数据可以传回 CPU 进行显示或进一步处理。讨论中提到了“同步”（或“sink”）这一术语：有时 CPU 必须与 GPU 同步，等待 GPU 完成其任务后再继续。在 PyTorch 中，许多过程默认是异步的，但显式的同步操作可以确保数据完整性并避免错误。大家一致认为，运行系统主要是由 CPU 驱动的，GPU 结果必须传回 CPU 才能进行面向用户的输出或后续步骤。

### 代码走读：关键组件

#### Dispatch_Fill 模式

小组检查了代码库中的一个 `dispatch_fill` 函数。其目的是用特定值填充张量。它通过根据数据类型进行分发来工作——不同类型映射到不同的内部实现，在 C++ 中本质上实现了一种泛型编程形式。该函数计算启动配置，然后将值填充到张量的数据指针中。其中涉及一个 `memory_copy` 步骤：一个版本使用源指针和 `fill_value` 将数据从一个位置复制到另一个位置。开发者确认 `tensor.data` 只是一个原始指针，而不是一个库对象。

#### 逐元素加法内核

开发者展示了一个逐元素加法内核。该内核执行逐元素加法：对于每个索引 `idx`，它计算 `result[idx] = a[idx] + b[idx]`。这是一种直接的并行模式，每个线程处理一个元素。内核包含一个约束：仅当 `idx` 小于 `num_elements` 时才进行计算，作为防止越界访问的保护。开发者提到，为了理解这类细节概念，他们通常更倾向于将代码复制到 AI 工具中并要求解释，而不是自己记住这些细节。

#### 转置内核

详细检查了转置 CUDA 内核代码。该内核处理二维转置，参数包括源、目标、维度大小、源跨度、目标跨度以及维度索引（dim0, dim1）。计算中使用 `idx` 来计算坐标，然后通过将坐标乘以跨度并加上偏移量来计算源和目标索引。`remainder` 操作用于在索引计算期间计算剩余维度。开发者指出，该内核包含对 INF（无穷大）值的处理——当值超出可表示范围时，它会产生 INF 而不是导致错误，这是可以接受的行为。

### 开发实践：AI 辅助与代码审查

开发者坦率地表示，大多数 CUDA 内核都是借助 AI 编写的——他们不会从头开始手写所有这些代码，因为那会太累。不过，他们强调自己清楚地理解每段代码的作用。使用 AI 仍然需要迭代：调整提示、处理编译错误、调试以及确保正确性。他们通常要求 AI 一次生成 50-100 行代码，而不是一次性生成整个组件，然后修复出现的小错误。一位参与者评论说，代码结构看起来很漂亮，考虑到其复杂性，开发者的方法令人印象深刻。
