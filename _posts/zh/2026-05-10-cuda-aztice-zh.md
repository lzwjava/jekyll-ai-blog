## Axono 项目：一个用 CUDA 编写的极简 PyTorch 类库

### 项目概览与动机

讨论开始时，一位参与者介绍了一个名为 [Axono](https://github.com/AxonoOfficial/Axono) 的项目，该项目托管在一个 GitHub 组织中。开发者将其描述为一个轻量级推理库，并指出它支持多种数据精度类型，包括 int8、int16、int32、int64、float32 和 float64。该库包含常用的算子：矩阵乘法（matmul）、加法以及简单的激活函数。当被问及它是否像 PyTorch 一样是一个 Python 库时，开发者确认了这一点，但强调开发速度已大幅放缓，因为只有一个人在做——进展令人疲惫。

该库主要面向 Linux 设计，虽然演示所用机器上存在 Windows 版本，但没有官方的 Windows 打包。开发者指出，当前展示的版本是 1.0，但澄清说演示的版本并非最新 1.0——而是一个较旧的版本。当被问及已发布了多少个版本时，回答是大约十几个到二十个。开发环境配备了一块 NVIDIA V100 GPU。

### 当前状态与 V2 重设计

对话转向了项目的结构。开发者解释说，当前的代码库（大约几千行）相当混乱，这促使他们为 V2 版本进行完全重写。V0 版本存在严重的时序问题，因此 V1 正在从头开始开发以取代它。然而，V1 尚未完成，因为整个过程相当麻烦。一个关键的架构变化是：V1 将不再支持纯 CUDA，而是强制使用 CUBLAS。不过，开发者指出，他们最终可能会为仍然需要纯 CUDA 的旧设备提供兼容性。

小组讨论了一个问题：Axono 能否用于编写一个小型神经网络，比如用于 MNIST 的数字分类器？该库目前不支持全连接层（Linear layer）——这是构建此类模型的关键需求。开发者承认了这一局限性，但指出由于 Axono 有矩阵乘法，理论上可以用数组来表示全连接层。大家一致认为这将是一个有趣的实验，一位参与者表示会获取代码并研究是否能在缺少 Linear 抽象的情况下实现一个极简的 MNIST。

### 张量操作与形状处理

一位参与者演示了如何声明一个张量变量并查看其形状。在进行矩阵乘法的演示时，他们列举了一个例子：矩阵 A 的形状为 (2, 3)，矩阵 B 的形状为 (3, 2)，结果形状应为 (2, 2)。在广播与标准矩阵乘法之间存在一些混淆——开发者澄清说，该库不会直接融合形状，而是将内部维度相乘，并生成外部维度作为结果形状。

关于形状变换，开发者表示目前仅提供了一个转置方法。没有通用的重塑（reshape）或形状变更方法。转置实现只是简单地交换行和列（A[i][j] 变为 A[j][i]），但这段代码相对冗长。当被问及更高维度的张量时，该库仅支持二维转置——它不处理同时转置多个维度的情况。开发者指出，约定是显式传递两个维度（dim0 和 dim1）。

### CUDA 实现：从 CPU 到 GPU 及其返回

#### 内核启动流程

开发者解释了底层的 CUDA 实现，从矩阵乘法开始。过程首先分配内存，设置启动配置，然后调用内核。在内核内部，一个简化的计算循环遍历行和列，生成结果。该库包含优化：一个名为 `matmul_optimized` 的内核采用列分块的方法，旨在使整体计算速度更快。

为了优化性能，开发者使用了块大小和共享内存。具体来说，他们将块大小参数移到临时模板中，将数据拉入共享内存块中以加速矩阵乘法。分块概念是将每个矩阵分割成小块（图块），以便进行更高效的计算——类似于 Flash Attention 中使用的分块技术。

#### 共享内存与内核结构

一位参与者要求在此上下文中解释共享内存。开发者承认自己没有一个完美的直观解释，将其描述为一种将矩阵块加载到共享内存（GPU 上更快的存储空间）中以加速重复访问的技术。代码还包含边界检查，以确保索引不会超出源张量和目标张量的范围。`idx` 变量用于计算转置操作中在源张量和目标张量中的位置。

矩阵乘法代码的跟踪显示，该库在启动内核之前会检查张量形状的兼容性。一个 `calculate_launch_config` 函数用于计算网格大小和块大小。块大小设置为 256。网格大小公式采用“向上取整”方法：`(num_elements + block_size - 1) / block_size`。一位参与者最初质疑这个公式，想知道为什么不能简单地将 `num_elements` 除以 `block_size`。开发者解释说，`+ block_size - 1` 的技巧确保了整数向上取整除法——当元素数量不能被整除时，该公式会向上取整以分配足够的块。这是在竞赛编程（OI）和通用 GPU 内核设计中的常见技术。

#### CPU 与 GPU 之间的内存传输

对话深入探讨了数据如何在 CPU 和 GPU 之间移动。开发者描述说，在内核执行期间，数据被“扔进”内核——这就是传输过程。当被问及哪个库处理这种传输时，开发者表示是他们自己的自定义包装器。然而，他们澄清说，数据实际上并不是在内核启动时从 CPU 移动到 GPU；张量从一开始就在 GPU 上初始化并分配内存。传递给内核的只是指向 GPU 内存的指针。然后内核直接对该 GPU 上的数据进行操作。

开发者打了一个比方：CPU 使用指针调用 GPU 函数，GPU 内核通过提供的指针访问该内存。他们强调 GPU 和 CPU 是分开运行的——CPU 不能直接访问 GPU 内存，因此 CUDA（或 CUBLAS）提供了调用 GPU 函数的机制。GPU 计算完成后，数据可以传回 CPU 进行显示或进一步处理。讨论了“同步”一词：有时 CPU 必须与 GPU 同步，等待 GPU 完成其任务后再继续。在 PyTorch 中，许多过程默认是异步的，但显式的同步操作可确保数据完整性并避免错误。大家一致认为，操作系统主要由 CPU 驱动，GPU 结果必须带回 CPU，以便面向用户输出或进行后续步骤。

### 代码走查：关键组件

#### Dispatch_Fill 模式

小组检查了代码库中的一个 `dispatch_fill` 函数。其目的是用特定值填充张量。它通过根据数据类型进行分发来工作——不同类型映射到不同的内部实现，本质上是在 C++ 中实现了一种泛型编程形式。该函数计算启动配置，然后将值填充到张量的数据指针中。涉及一个 `memory_copy` 步骤：一个版本使用源指针和一个 `fill_value` 将数据从一个位置复制到另一个位置。开发者确认 `tensor.data` 只是一个原始指针，而不是一个库对象。

#### 逐元素加法内核

开发者展示了一个逐元素加法内核。该内核执行逐元素加法：对于每个索引 `idx`，计算 `result[idx] = a[idx] + b[idx]`。这是一个直接的并行模式，每个线程处理一个元素。该内核包含一个约束：只有当 `idx` 小于 `num_elements` 时才进行计算，作为防止越界访问的保护。开发者指出，对于理解这类细节概念，他们通常更倾向于将代码复制到 AI 工具中并请求解释，而不是自己记住细节。

#### 转置内核

详细检查了转置 CUDA 内核代码。该内核处理二维转置，参数包括源、目标、维度大小、源跨度、目标跨度以及维度索引（dim0, dim1）。计算使用 `idx` 来计算坐标，然后通过将坐标乘以跨度并加上偏移量来计算源索引和目标索引。使用取余运算来计算索引计算中的剩余维度。开发者指出，该内核包含对 INF（无穷大）值的处理——当值超出可表示范围时，会产生 INF 而不是错误，这是可以接受的行为。

### 开发实践：AI 辅助与代码审查

开发者坦率地表示，大部分 CUDA 内核都是在 AI 辅助下编写的——他们不会从头手动编写所有这些代码，因为那太累了。然而，他们强调自己清楚每段代码的作用。使用 AI 仍然需要迭代：调整提示、处理编译错误、调试以及确保正确性。他们通常要求 AI 一次生成 50-100 行代码，而不是一次性生成整个组件，然后逐个修复小错误。一位参与者评论说，代码结构看起来非常精致，考虑到复杂性，开发者的方法令人印象深刻。

## 竞争性 AI 工程与模型优化

开发者展示了他的竞赛 PPT。团队名称是“everywhere we go”（原始幻灯片中有一个小拼写错误）。该团队最初还有另一名成员，用开发者的话说，“什么都没做”——他们在网上找到了这位队友，但那个人没有提供任何实质性贡献。开发者承认在香港很难找到可靠的队友；他不认识其他有类似兴趣的人。对于后续的一场竞赛，他们已经与一名研究生组队，这名研究生可以提供有意义的帮助，不像典型的本科生。

### 竞赛工作流程与技术方法

该竞赛涉及一个需要从图形输入中推导出答案的问题。开发者的流程第一步使用了 OCR 识别，具体是 PPOCR（来自百度 PaddlePaddle 框架的 PaddleOCR）。他指出，在香港，很多人不喜欢国内的中文工具，更喜欢西方替代品，但开发者使用 PaddleOCR 没有这种偏见，并且发现它效果很好。OCR 结果产生了字符串提取，团队将其与检测网络（类似于 YOLO）结合，在识别之前定位文本区域。

竞赛期间的排行榜指标包括准确率分数（一个例子为 0.47381），记录于 10 月 27 日。开发者指出，具体指标细节有些忘记了，但代表了识别结果和字符串提取质量。竞赛中排名靠前的团队使用了多种优化技巧来实现更快的推理速度，尽管开发者记不清他们所有的具体技术。

### 当前竞赛：模型服务优化

开发者目前正在参加另一场专注于模型服务优化的竞赛。这场竞赛开始时约有 480 支队伍，经过一轮淘汰后迅速缩减到 16 支决赛队伍。开发者的团队在 16 名决赛选手中排名第 8，团队名称是“forgive me out”。他们的队友是来自华东师范大学的一名研究生。

竞赛指标包括准确率（上限为 0.7——得分超过 0.7 视为 1.0，大多数团队轻松达到 0.7）、TTFT（首令牌时间）和吞吐量（每秒令牌数）。开发者指出 TTFT 和吞吐量才是真正困难的指标——准确率基本上是保底的。他们已经在一个月左右的时间内提交了 54 次累计提交，其中 27 次提交计入排名。他们的吞吐量得分是 38（无论竞赛使用什么尺度）。排名第一的团队在所有三个指标上都领先。

对于这场竞赛，开发者从头开始手动编写了解决方案，理由是 AI 生成的代码对此类工作来说太容易出错。他们花了大约两周时间将模型编写成可部署的图表示形式。他们目前处于最后阶段，前三名队伍将晋级在越南举行的决赛。
