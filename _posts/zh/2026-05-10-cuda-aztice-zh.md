## Axono 项目：一个用 CUDA 编写的类 PyTorch 极简库

### 项目概览与动机

讨论从一位参与者介绍一个名为 [Axono](https://github.com/AxonoOfficial/Axono) 的项目开始，该项目托管在一个 GitHub 组织下。开发者将其描述为一个轻量级推理库，并表示它支持多种数据精度类型，包括 int8、int16、int32、int64、float32 和 float64。该库包含一些常用的运算符：矩阵乘法（matmul）、加法以及简单的激活函数。当被问及它是否像 PyTorch 一样是一个 Python 库时，开发者给出了肯定的回答，但强调由于只有一个人在进行开发，进展已经大大放缓——这使得推进工作非常耗费精力。

该库主要面向 Linux 设计，虽然演示所用的机器上存在一个 Windows 版本，但没有官方的 Windows 打包版本。开发者指出，当前展示的版本 1.0 并非最新的 1.0 版本，而是一个较旧的发行版。当被问及已经发布了多少个版本时，答案大约是十来个到二十个。开发环境是一台配备了 NVIDIA V100 GPU 的机器。

### 当前状态与 V2 重新设计

对话转向了项目的结构。开发者解释说，当前的代码库（大约几千行）非常混乱，这促使他们决定为 V2 版本进行完全重写。V0 版本存在严重的时序问题，因此 V1 版本是从头开始开发的，旨在取代它。然而，V1 版本尚未完成，因为整个过程非常麻烦。一个关键的架构变化是，V1 版本将不再支持纯 CUDA，而是强制要求使用 CUBLAS。不过，开发者提到，他们最终可能会为那些仍需要使用纯 CUDA 的老旧设备提供兼容性支持。

团队讨论了一个问题：Axono 能否用来编写一个小型神经网络，比如手写数字识别（MNIST）的分类器。该库目前不支持创建此类模型所需的关键组件——Linear 层。开发者承认了这一局限性，但指出，既然 Axono 具备矩阵乘法功能，理论上可以使用数组来表示 Linear 层。大家一致认为这将是一个有趣的实验，一位参与者表示会获取代码并研究一下，看看是否能在缺少 Linear 抽象的情况下实现一个极简版的 MNIST 模型。

### 张量操作与形状处理

一位参与者演示了如何声明一个张量变量并查看其形状。在演示矩阵乘法时，他们举了一个例子：矩阵 A 的形状为 (2, 3)，矩阵 B 的形状为 (3, 2)，并指出结果应该具有形状 (2, 2)。关于广播机制与标准矩阵乘法之间出现了一些混淆——开发者澄清说，该库并不会直接融合形状；而是将内部维度相乘，外部维度则作为结果的形状。

关于形状变换，开发者表示目前只提供了 transpose（转置）方法。没有通用的 reshape（重塑）或形状改变方法可用。转置的实现仅仅是交换行和列（A[i][j] 变为 A[j][i]），但实现的代码相对较长。当被问及更高维度的张量时，该库仅支持二维转置——无法同时处理多个维度的转置。开发者指出，惯例是显式地传递两个维度（dim0 和 dim1）。

### CUDA 实现：从 CPU 到 GPU 再返回

#### 内核启动流程

开发者从矩阵乘法开始解释了底层的 CUDA 实现。流程首先从分配内存开始，然后设置启动配置，最后调用内核。在内核内部，通过一个简化的行和列循环计算来产生结果。该库包含一些优化：其中一个内核被称为 `matmul_optimized`，它采用了一种列分块（column tile）的方法，旨在使整体计算运行得更快。

为了优化性能，开发者使用了块大小和共享内存。具体来说，他们将块大小参数移入一个临时模板中，将数据拉取到共享内存块中，以加速矩阵乘法。分块（tile）的概念是将每个矩阵分割成小块（tiles）以进行更高效的计算——类似于 Flash Attention 中使用的分块技术。

#### 共享内存与内核结构

一位参与者要求解释一下此处共享内存的概念。开发者坦言自己没有一个完美的直观解释，将其描述为一种将矩阵块加载到共享内存（GPU 上速度更快的内存空间）中以加速重复访问的技术。代码中还包含了边界检查，以确保索引不超出源张量和目标张量的边界。`idx` 变量用于在转置操作中计算源张量和目标张量中的位置。

对矩阵乘法代码的追踪显示，该库在启动内核之前会检查张量形状的兼容性。一个 `calculate_launch_config` 函数负责计算网格大小和块大小。块大小被设置为 256。网格大小的计算公式采用了一种“向上取整”的方法：`(num_elements + block_size - 1) / block_size`。一位参与者最初对这个公式提出了疑问，想知道为什么不直接用 `num_elements` 除以 `block_size`。开发者解释说，`+ block_size - 1` 这个技巧确保了整数除法下的向上取整——当元素数量不能被整除时，这个公式会向上取整，以分配足够的块。这是竞赛编程（OI）和通用 GPU 内核设计中常见的技术。

#### CPU 与 GPU 之间的内存传输

对话深入探讨了数据如何在 CPU 和 GPU 之间移动。开发者描述说，在内核执行期间，数据被“扔进”内核中——这就是传输过程。当被问及是哪个库处理这种传输时，开发者表示是他们自己的自定义封装。然而，他们澄清说，数据实际上并非在内核启动时从 CPU 移动到 GPU；张量从初始化开始就在 GPU 上分配好了。传递给内核的仅仅是指向 GPU 内存的指针。然后，内核直接在 GPU 内存中的数据上进行操作。

开发者打了个比方：CPU 使用指针来调用 GPU 函数，而 GPU 内核则通过提供的指针访问那块内存。他们强调，GPU 和 CPU 是独立运行的——CPU 不能直接访问 GPU 内存，因此 CUDA（或 CUBLAS）提供了调用 GPU 函数的机制。GPU 计算完成后，数据可以被传回 CPU 进行显示或进一步处理。讨论中还提到了“同步”的概念：有时 CPU 必须与 GPU 同步，等待 GPU 完成其任务后才能继续。在 PyTorch 中，许多操作默认是异步的，但显式的同步操作可以确保数据的完整性并避免错误。大家一致认为，操作系统主要是由 CPU 驱动的，GPU 的结果必须被带回 CPU，以供面向用户的输出或后续步骤使用。

### 代码走查：关键组件

#### Dispatch_Fill 模式

团队检查了代码库中的一个 `dispatch_fill` 函数。其目的是用特定值填充一个张量。它的工作方式是依据数据类型进行分发——不同的类型映射到不同的内部实现，本质上是在 C++ 中实现了一种泛型编程。该函数计算启动配置，然后将值填充到张量的数据指针中。其中涉及一步 `memory_copy`：一个版本使用源指针和一个 `fill_value` 将数据从一个位置复制到另一个位置。开发者确认 `tensor.data` 只是一个裸指针，而不是一个库对象。

#### 逐元素加法内核

开发者展示了一个逐元素加法内核。该内核执行逐元素加法：对于每个索引 `idx`，计算 `result[idx] = a[idx] + b[idx]`。这是一种直接的并行模式，每个线程处理一个元素。该内核包含一个约束：仅当 `idx` 小于 `num_elements` 时才进行计算，这是为了防止越界访问。开发者提到，对于理解这些细节概念，他们通常更喜欢将代码复制到 AI 工具中并请求解释，而不是自己死记硬背。

#### 转置内核

团队详细检查了 CUDA 转置内核的代码。该内核处理二维转置，参数包括源、目标、维度大小、源步长、目标步长以及维度索引（dim0, dim1）。计算过程使用 `idx` 来计算坐标，然后通过将坐标乘以步长并加上偏移量来计算源索引和目标索引。`remainder` 运算用于在索引计算过程中计算剩余维度。开发者指出，该内核包含了对 INF（无穷大）值的处理——当一个值超出可表示范围时，会产生 INF 而不是引发错误，这是可以接受的行为。

### 开发实践：AI 辅助与代码审查

开发者坦率地表示，大多数 CUDA 内核都是在 AI 辅助下编写的——他们不会从头开始手动编写所有这些代码，因为那太耗费精力了。然而，他们强调自己清楚地理解每一段代码的作用。使用 AI 仍然需要迭代：调整提示语、处理编译错误、调试以及确保正确性。他们通常是让 AI 一次生成 50-100 行代码，而不是一次生成整个组件，然后逐步修复出现的小错误。一位参与者评论说，代码结构看起来非常精致，考虑到其复杂性，开发者的方法令人印象深刻。

### 竞赛流程与技术方法

该竞赛的问题要求从图形输入中推导出答案。开发者的流程第一步是使用 OCR 识别，具体来说是 PPOCR（百度飞桨 PaddlePaddle 框架中的 OCR 工具）。他们提到，在香港很多人不喜欢国内的国产工具，而偏爱西方的替代品，但开发者使用 PaddleOCR 时没有这种偏见，并认为它效果很好。OCR 结果产生字符串提取，团队将其与一个检测网络（类似于 YOLO）结合，在识别之前定位文本区域。

竞赛期间的排行榜指标包括一个准确率分数（在一个示例中为 0.47381），记录于 10 月 27 日。开发者指出，具体的指标细节有些忘记了，但它代表了识别结果和字符串提取质量。竞赛中表现最好的队伍使用了多种优化技巧来实现更快的推理速度，不过开发者记不清他们所有的具体技术了。

### 当前竞赛：模型服务优化

开发者目前正在参加另一场专注于模型服务优化的竞赛。该竞赛开始时约有 480 支队伍，经过一轮淘汰赛后迅速缩减到 16 支决赛队伍。开发者的团队在这 16 支决赛队伍中排名第 8，使用的队名是“forgive me out”。他们的队友是来自华东师范大学的一名研究生。

竞赛的指标包括准确率（上限为 0.7——分数高于 0.7 则视为 1.0，大多数队伍很容易达到 0.7）、TTFT（首个令牌生成时间）和吞吐量（每秒令牌数）。开发者指出，TTFT 和吞吐量才是真正困难的指标——准确率基本上算是送分题。他们在大约一个月的时间内提交了 54 次，其中 27 次提交被计入排名。他们的吞吐量分数是 38（基于竞赛使用的任何量纲）。排名第一的队伍在所有三项指标上都领先。

对于这次竞赛，开发者完全手动编写了解决方案，理由是 AI 生成的代码对于这类工作来说太容易出错。他们花了大约两周时间将模型编写成可以部署的图表示形式。他们目前处于最后阶段，排名前三的队伍将晋级在越南举行的最终活动。
