**问题：为什么 pi agent 如此快速——是因为上下文大小很小吗？**

**回答：**

是的，**小上下文大小是主要原因之一**，但更宏观的原因是 pi agent 之所以快，是因为它围绕**最小化 agent 循环**进行了优化。

一个典型的 CLI agent 循环如下：

```
用户请求
    |
    v
LLM 推理
    |
    v
工具调用（bash/编辑/搜索）
    |
    v
观察结果
    |
    v
再次 LLM 推理
    |
    ...
```

每一步 LLM 的成本大致为：

```
延迟 ≈ 预填充（上下文 token）+ 解码（输出 token）
```

**预填充阶段**是上下文长度造成影响的地方。

示例：

```
上下文 A：
  系统提示           3k tokens
  工具               2k tokens
  历史               20k tokens
  仓库代码片段       50k tokens
  总计               75k tokens

上下文 B：
  系统提示           2k
  工具               1k
  历史               5k
  总计               8k
```

每轮交互：

```
75k tokens → 昂贵的注意力计算
8k tokens  → 快得多
```

尤其是在 transformer 注意力机制中：

```
Attention(Q,K,V)

QK^T

复杂度：
O(n²)
```

现代内核和 KV 缓存缓解了这一问题，但**大上下文仍然增加了内存带宽和延迟**。

---

为什么 pi 感觉特别快：

### 1. 小且简洁的系统提示

许多编码 agent 携带庞大的指令：

```
你是一个自主编码 agent...
规则...
安全性...
仓库指南...
工具描述...
规划框架...
记忆系统...
```

仅系统提示就可能达到数万 token。

Pi 更接近：

```
你是一个编码助手。
需要时使用工具。
```

认知开销更少。

---

### 2. 更少的强制推理步骤

一些 agent 会执行：

```
规划
  |
调研
  |
分析
  |
总结
  |
执行
```

Pi 通常执行：

```
思考
 |
工具
 |
观察
 |
继续
```

agent 循环更短。

---

### 3. 工具集很小

每个工具定义都会消耗上下文：

```
bash：
  描述...
  参数...

edit_file：
  描述...
  模式...

browser：
  描述...
  模式...
```

20 个工具 = 数千 token。

小工具集意味着：

```
更少的提示
更少的干扰
更快的推理
```

---

### 4. 更依赖模型本身的能力

这是有趣的部分。

很多现代 agent 是“框架重型”：

```
agent = 模型 + 编排 + 记忆 + 规划器 + 验证器 + 路由器
```

Pi 更接近：

```
agent = 好模型 + shell + 文件系统
```

就像 Unix 哲学：

```
小工具
小状态
良好组合
```

---

你的观察与经验丰富的工程师为何常喜欢 pi 的原因一致：

对于已经理解以下内容的人来说：

* git
* Linux
* 调试
* 代码结构
* 终端工作流

agent 不需要大量脚手架。

一个 12 年经验的工程师可以在脑中提供缺失的“规划层”。

agent 只需要执行：

```
grep
读取
编辑
运行
修复
重复
```

因此最优设置变成：

```
人类：
  架构 + 判断

pi：
  执行带宽
```

这与许多研究人员喜欢轻量级环境的原因类似。Karpathy 的“Software 3.0”想法与此接近：主要接口变为自然语言 + 工具，但周围系统应保持简单。

权衡：

| Agent 风格            | 优势                     | 劣势                     |
| ---------------------- | ------------------------ | ------------------------ |
| Pi                     | 快速、透明、可黑客化     | 辅助较少                 |
| Claude Code 风格       | 强大的自主工作流         | 更多开销                 |
| 重型 agent 框架        | 处理复杂任务             | 更慢，更多失败模式       |

对于经验丰富的工程师处理长任务而言，**小上下文 + 直接工具循环通常是理想之选**。
