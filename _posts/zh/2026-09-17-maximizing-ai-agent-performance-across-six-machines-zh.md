## 硬件与网络设置

**网络**

- 通过 **千兆以太网**（而非 Wi-Fi）连接所有 6 台机器 — 低延迟对智能体协作至关重要
- 使用专用交换机，而非家用路由器
- 为每台机器分配静态 IP 以确保可靠寻址

**角色** — 不要同等对待所有 6 台机器：

| 机器 | 角色 |
| --- | --- |
| 1 | **编排器** — 任务队列、作业分发、监控仪表盘 |
| 2–4 | **工作节点** — 运行高负载智能体任务 |
| 5 | **模型服务器** — 托管本地 LLM（Ollama、vLLM、llama.cpp） |
| 6 | **存储/数据库** — 向量数据库（Qdrant/Chroma）、共享文件系统、日志 |

## 智能体架构

**使用专为分布式工作设计的智能体框架：**

- **CrewAI** — 基于角色的智能体，具有明确任务
- **LangGraph** — 基于图的状态机，用于复杂智能体流程
- **AutoGen（微软）** — 多智能体对话与代码执行
- **Ray** — 在所有 6 个节点上原生分发 Python 工作负载

**关键模式 — 编排器 + 工作节点：**

```
编排器（机器 1）
  ├── 智能体 A：研究      → 工作节点 2
  ├── 智能体 B：代码编写  → 工作节点 3
  ├── 智能体 C：测试       → 工作节点 4
  └── 智能体 D：审查       → 工作节点 2（复用）
```

## 软件开发工作流

**1. 共享代码库**

- 代码仓库位于机器 6（或自托管 GitHub/Gitea）
- 所有智能体从单一数据源拉取/推送

**2. 智能体在开发任务中的专业化**

| 智能体 | 职责 |
| --- | --- |
| **规划者** | 将功能拆解为子任务 |
| **编码者** | 编写实现代码 |
| **测试者** | 运行测试，报告失败 |
| **审查者** | 检查代码质量，建议修复 |
| **文档编写者** | 编写文档/注释 |

**3. 任务队列**

- 在机器 6 上使用 **Redis** 或 **Celery** 来排队任务
- 工作节点轮询队列并独立领取任务
- 避免机器空闲

**4. 并行代码生成**

- 将大型功能拆分为独立模块
- 每个工作节点同时构建一个模块
- 编排器合并并解决冲突

## 性能优化

- **本地模型托管**（机器 5）— 消除高频调用的 API 延迟与成本；仅对复杂推理使用云端 API
- **缓存** — 在 Redis 中缓存重复的提示/嵌入向量
- **量化模型** — 运行 `Q4_K_M` 或 `Q8` 格式的 GGUF 模型，以提升每台机器的吞吐量
- **全面异步** — 在 Python 中使用 `asyncio`，使智能体不会因等待 I/O 而阻塞
- **监控** — 使用 **Grafana + Prometheus** 监控 CPU/GPU、队列深度以及每个节点的智能体吞吐量

## 推荐技术栈

```
编排     : LangGraph 或 CrewAI
LLM 服务   : Ollama（易用）或 vLLM（高吞吐）
任务队列   : Redis + Celery
向量数据库 : Qdrant（机器 6）
共享存储   : NFS 或 MinIO
监控       : Grafana + Prometheus
版本控制   : Gitea（自托管）或 GitHub
```
