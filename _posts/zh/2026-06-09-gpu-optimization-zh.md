他们讨论了最近的比赛和参与者的表现。一位参与者请另一位简要展示其近期成果和比赛进展，特指那个曾声称排名第一但结果尚未公布的比赛。对方澄清比赛尚未结束，目前不显示排名。有人问是否是百度比赛，对方确认。询问比赛的全英文名称，对方回答是 Baidu CTI，并指出它没有英文名。

话题转向 CUDA Graph。一位参与者提到自己一直在进一步理解 CUDA Graph，特别是其工作原理。他们讨论了 CUDA Graph 的工作方式：它记录 CPU 通常会向 GPU 发起的核函数调用，使 GPU 能够直接执行这些调用而无需 CPU 参与。一位参与者询问这个图是真实的数据结构还是只是一个概念，对方解释说是对 CPU 调用 GPU 过程的记录，这些调用被固定成一个图。当 GPU 下次运行时，不再需要 CPU 发出指令；CPU 可以退出，由 GPU 全权处理。有人问记录间隔如何指定——是每秒、每毫秒，还是基于一定数量的指令。回答是没有间隔，它以非阻塞方式执行。

一位参与者承认自己不理解阻塞与非阻塞的区别，对方解释通常运行图会导致阻塞，因为 CPU 必须等待发出指令，但记录 CUDA 图后，GPU 不再需要等待 CPU，可以直接执行之前记录的指令。一位参与者问 GPU 执行完后如何通知 CPU，对方解释图的结果会直接交回给 CPU，CPU 随后继续后续任务。需要注意的是，并非所有 CPU 指令都会被记录到 CUDA 图中——只有特定指令，尤其是 GPU 擅长的矩阵和浮点运算指令。一位参与者问为什么 CUDA Graph 常与优化关联，对方解释它能加速性能，因为 CPU 阻塞耗时太长；记录后通常会加快速度。他们讨论了为什么需要处理 CUDA Graph 这样底层的概念，而不是简单通过 PyTorch 将数据移到 GPU。回答是即使将数据移到 GPU，运行模型时 CPU 仍需数千次发出指令，但使用 CUDA Graph，CPU 只需告诉 GPU 一次，GPU 便会自动记录并重复操作。

随后他们讨论了大模型中的权重和参数概念。一位参与者问权重和参数的区别，对方澄清参数通常由 CPU 处理，而权重是 GPU 的职责。权重因层数多而占用大量空间，需要高带宽内存（HBM），速度可达数百 GB/s 甚至 TB/s。对方指出 HBM3 提供 192 GB 显存，TB 级速度对于非常大的模型是合理的，但推理时 GB 级速度通常足够，而训练则需要更高优先级。

话题转向参与者之前的比赛胜利，他们优化了推理。当被问及使用了什么技术使其排名第一时，对方回答比赛尚未结束，细节不能透露。一位参与者随后问如何分析给定 GPU（如 H100、H200、4090、3090）能处理多大尺寸的本地模型进行推理。回答主要取决于可用显存。例如，12 GB 显存只能运行小模型或量化模型，上下文长度也至关重要——10,000 tokens 与 100,000 tokens 差异巨大，量化类型（如 4-bit 与 8-bit）同样重要。5–8 GB 的模型可通过 GGUF 加载，但更大的模型无法容纳，上下文大小可能限制在 2048 或 10,000 以下。针对小型设备的优化是他们工作的一部分，使用了 Flash Attention 等技术。

他们讨论了 vLLM 和 SGLang。一位参与者问 SGLang 的原理以及为何能显著减少 KV cache 使用。对方解释 SGLang 与 vLLM 类似，提供分布式处理优化，通过预处理和隔离每个用户的内存来处理多个设备。对方指出这类框架通常与数学公司绑定，无需特别关注，因为批处理处理和用户隔离由底层框架处理。一位参与者问为什么面向公众的服务器使用 vLLM 和 SGLang，而 Llama.cpp 更偏向单用户，回答是 vLLM 和 SGLang 更便于部署，尽管自定义优化可能更快，但公司通常将其保密。

随后他们讨论了 KV cache。一位参与者问 K 和 V 指什么，以及有多少优化空间。对方解释 KV cache 指的是上下文；没有它，要推理一个新 token，需要重新处理所有之前的 token，但有了 KV cache，只需前一个 token 的缓存信息，省去了这一步。一位参与者澄清前一个 token 已包含绑定的上下文信息，因此只需查找即可生成下一个 token。对方同意这在概念上相似，但性能优化会揭示差异。

话题转向 Flash Attention。一位参与者提到 Flash Attention 的作者声称，在通用 NVIDIA 硬件上进行软件优化，可使 DeepSeek V4 等模型达到每秒 500 tokens，与 Groq 等定制芯片相媲美。对方同意定制芯片如 FPGA 通常更快，但经过适当优化的 NVIDIA 硬件也极具竞争力。他们简短提到 Groq 公司可能已被 NVIDIA 收购，但参与者不确定。一位参与者问 NVIDIA 芯片经过适当优化是否确实能达到每秒 500 tokens 甚至更高，对方肯定 NVIDIA 技术很好，只是价格昂贵。

他们讨论了 TensorRT 和 cuDNN。一位参与者问这些工具的作用，对方解释 TensorRT 是一个加速引擎，也与 CUDA Graph 绑定，比 PyTorch 更快，因为它专门针对加速优化，但使用起来非常困难。cuDNN 是一个加速算子库，类似于 cuBLAS，专为线性代数和 AI 加速设计。一位参与者注意到 cuBLAS 频繁出现，问为什么许多操作最终都依赖它。对方解释 cuBLAS 是专为 NVIDIA GPU 设计的矩阵加速库，比普通 CUDA 代码快得多，而 cuBLASLt（cuBLAS Light）是一个更灵活的 API，可能更快。一位参与者观察到 CUDA 本身已是高级 API，对方同意，并补充说他们欣赏 NVIDIA 加速产品的易用性。他们讨论了 NVIDIA 的护城河，指出其更多在于软件而非硬件。一位参与者问 CUDA 驱动和 CUDA 工具包的区别，对方澄清工具包面向开发者，而驱动是工具包运行所需的基础层。

随后他们讨论了 Triton。一位参与者问提到 CUDA 时会想到哪些项目，对方提到算子加速和算子融合，他们在比赛中使用过。对方指出 vLLM 使用了此类技术，尽管它依赖 PyTorch。一位参与者问 Triton 是什么，对方解释它是 CUDA 的简化版本，也能在 AMD 设备上运行。它是一种用于编写算子的语言，易于使用，通常能达到原生 CUDA 性能的 85–95%，但原生 CUDA 需要更多调试。一位参与者问精通 CUDA 的人是否在 NVIDIA 或 OpenAI 等公司工作，对方同意，但指出自己个人使用 Triton 多于 CUDA，仅在极端优化时才使用 CUDA。他们确认 Triton 是目前最标准的算子融合库，并广泛用于 SGLang 等开源框架。

话题转向混合专家模型（MoE）。一位参与者问 MoE 和 SFT 的最新进展，对方表示自己因做推理加速而有一定了解。他们解释每个专家产生一个输出，然后聚合为最终 logit，但不熟悉专家如何划分（如金融与编程），因为他们专注于加速而非研究。一位参与者问他们常用于推理加速的模型有哪些，对方回答取决于比赛，但会使用 Qwen 系列和一些序列模型。日常使用中，他们使用 Gemini，它虽非开源，但便于辅助工作。他们不优化 Gemini，而是优化 Qwen 等开源模型。

一位参与者问为什么参与者的优化成果不在网上公开，而必须编写自定义代码。对方解释虽然网上存在一些优化，但很少，自定义代码比标准实现更快，因为他们追求极致速度同时保持高精度。他们不会减少层数以免影响精度。一位参与者问加速是否涉及融合矩阵运算、将 CPU 任务移至 GPU 或预计算。对方确认预计算很常见，CUDA Graph 需要先记录图。他们讨论了 PyTorch 的编译功能，指出虽然主流模型常声称 PyTorch 编译最快，但手写代码总是更快，因为它更具针对性且避免了开销。不过，他们承认 PyTorch 编译是一个强大工具，但在定制方面不够方便。

他们再次讨论了 Flash Attention。一位参与者问为什么 Flash Attention 使用分块方法将注意力计算从二次内存移至 SRAM。对方解释 SRAM 是静态内存，地址不移动，这有助于运行图。当被问及为什么需要分块而不是一次性将所有内容移至 SRAM 时，对方说是因为 SRAM 无法容纳所有内容，而 CPU 更擅长分块处理。一位参与者问参与者是否渴望为推理创建类似的硬件级优化，对方说有可能，但目前专注于模型优化。

他们讨论了 Qwen 模型系列。一位参与者问对方运行多大尺寸的 Qwen，回答是 2B，因为小模型足以进行优化——如果在小模型上有效，在大模型上也会有效。他们确认使用 Triton 编写自定义推理代码，并通过算子融合进行优化。一位参与者问他们的优化代码是否比 Llama.cpp 或 vLLM 更快，对方说通常更快，尽管 vLLM 更方便且通用。自定义代码通常为 500 到 2,000 行 Python，CUDA 代码则更长。一位参与者问对方是否遇到很多更资深的人士，对方说很少，因为大多数人更喜欢使用 vLLM 或 Claude Code 等自动化工具，他们认为这失去了比赛的真正精神。对方指出比赛组织者会审查提交内容，检查代码是否由 AI 生成，并评估参与者的背景，因此即使有人以薄弱简历获得第一名，也可能受到审查。
