问题：TCP如何管理流量控制？

回答：

TCP的流量控制回答一个特定问题：

> **发送方能以多快的速度传输数据，而不会溢出接收方的缓冲区？**

关键机制是接收方通告的**接收窗口（`rwnd`）**。

### 1. 接收方通告可用缓冲区大小

假设接收方有一个TCP接收缓冲区：

```text
+---------------------------------------------+
| 已消费的数据 | 已接收的数据 | 空闲空间       |
+---------------------------------------------+
                     ↑           ↑
                 字节数       rwnd = 8 KB
```

接收方在其TCP头部中填入`rwnd = 8192`。

概念上：

```text
接收方 → 发送方：
ACK=1000
Window=8192
```

这意味着：

```text
"我已收到至字节999为止的所有数据，
你最多可以有8192个未确认的字节在途。"
```

---

### 2. 发送方跟踪可用窗口

TCP序列号是面向字节的。

假设：

```text
SND.UNA = 1000   # 最老的未确认字节
SND.NXT = 5000   # 发送方将要发送的下一个字节
rwnd    = 8192
```

那么：

```text
bytes_in_flight = SND.NXT - SND.UNA
                = 4000
```

因此发送方可以发送：

```text
rwnd - bytes_in_flight
= 8192 - 4000
= 4192 字节
```

基本约束是：

```text
SND.NXT - SND.UNA <= rwnd
```

或等价地：

```text
in_flight <= receive_window
```

---

### 3. 随着接收方消费数据，窗口打开

想象：

```text
rwnd = 8192
```

发送方填满窗口：

```text
发送方 ──────────────── 8192 字节 ────────────────> 接收方

                                               缓冲区：
                                               [########]
                                               空闲 = 0
                                               rwnd = 0
```

接收方的应用程序随后读取4 KB：

```text
应用程序
     │
     │ read()
     ▼
+------------------+
| TCP 接收缓冲区   |
|      4 KB 空闲   |
+------------------+
```

TCP可以通告：

```text
ACK=...
Window=4096
```

现在发送方可以再发送4 KB。

因此流量控制持续遵循以下流程：

```text
应用程序消费数据
        ↓
接收缓冲区获得空闲空间
        ↓
接收方通告更大的 rwnd
        ↓
发送方被允许发送更多数据
```

---

## 4. 当接收方太慢时会发生什么？

假设：

```text
接收方缓冲区 = 64 KB
应用程序消费速率 = 1 MB/s
发送方速率       = 10 MB/s
```

接收缓冲区被填满：

```text
                    TCP 接收缓冲区
                ┌──────────────────────┐
传入数据 ──────►│######################│
                └──────────────────────┘
                         空闲 = 0
                         rwnd = 0
```

接收方发送：

```text
Window = 0
```

发送方必须停止发送新数据。

这就是 **TCP 流量控制**。

它防止了：

```text
快速发送方
    ↓
慢速接收方
    ↓
接收方缓冲区溢出
```

---

## 5. 零窗口探测

当以下情况出现时，会有一个微妙的问题：

```text
接收方 → 发送方：
rwnd = 0
```

如果接收方后续打开了窗口，但发送方错过了这个更新怎么办？

TCP 有**零窗口探测**机制。

发送方定期发送一个小探测包，实质上是在询问：

```text
"你当前的接收窗口是多少？"
```

接收方用其当前的ACK/窗口进行响应。

因此零窗口不会永久性地导致连接死锁。

---

## 6. 窗口缩放

TCP头部中的窗口字段只有**16位**。

原始最大窗口：

```text
2^16 - 1 = 65,535 字节
```

这对于现代高带宽/高延迟链路来说太小了。

因此TCP在三次握手期间协商**窗口缩放**选项。

例如：

```text
窗口字段 = 32768
缩放因子 = 7
```

有效窗口：

```text
32768 << 7
= 4,194,304 字节
≈ 4 MB
```

缩放因子在以下过程中协商：

```text
SYN
SYN-ACK
```

然后应用于后续的窗口通告。

# 流量控制 vs 拥塞控制

这个区别极其重要。

TCP实际上有**两个独立的限制**：

```text
                   发送方
                     │
             ┌───────┴────────┐
             │                │
          rwnd             cwnd
             │                │
       接收方限制        网络限制
             │                │
             └───────┬────────┘
                     ↓
             实际发送窗口
```

近似地：

```text
send_window = min(rwnd, cwnd)
```

### `rwnd` — 流量控制

由以下控制：

```text
接收方
```

问题：

> "我的接收缓冲区还能处理更多数据吗？"

### `cwnd` — 拥塞控制

由以下控制：

```text
发送方
```

基于对网络的观察。

问题：

> "网络还能处理更多数据吗？"

因此想象：

```text
rwnd = 10 MB
cwnd = 2 MB

send_window = min(10 MB, 2 MB)
            = 2 MB
```

接收方没问题；**网络**是瓶颈。

反过来：

```text
rwnd = 64 KB
cwnd = 10 MB

send_window = 64 KB
```

网络没问题；**接收方**是瓶颈。

## 思维模型

你可以将TCP的流量控制机制简化为以下内容：

```text
接收方：

    接收缓冲区
          │
          ▼
     空闲容量
          │
          ▼
         rwnd
          │
          │ 在ACK中通告
          ▼
发送方：

     只有在以下条件时才能发送

     unacked_bytes < rwnd
```

在实际的TCP中：

```text
                    ┌── 接收方 ──► rwnd
                    │
应用程序 ──► TCP ┤
                    │
                    └── 网络 ───► cwnd

              可发送量 =
              min(rwnd, cwnd)
```

有趣的是，**TCP流量控制本质上是一个滑动窗口协议**：ACK移动发送方窗口的左边缘，而通告的接收窗口决定了右边缘可以延伸多远。

如果你想从数据包层面理解TCP，下一步有用的做法是逐包分析**10个数据包，每个包后都标注`SEQ`、`ACK`、`SND.UNA`、`SND.NXT`、`RCV.NXT`、`rwnd`和`cwnd`**。
