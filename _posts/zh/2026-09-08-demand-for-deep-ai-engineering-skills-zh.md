问题：除了“大语言模型应用开发”之外，是否还会有对工程师的强烈需求——特别是预训练、后训练、CUDA/GPU 和推理基础设施？

答案：**是的。我认为这将是未来5到10年发展起来的最重要的工程劳动力市场之一。** 但我倾向于将其分层，因为“大语言模型工程师”将变得高度专业化。

### 技术栈大致如下

```text
                 AI 产品 / 智能体
                        │
              ┌─────────┴─────────┐
              │   大语言模型应用   │
              │   智能体 / RAG     │
              └─────────┬─────────┘
                        │
              ┌─────────┴─────────┐
              │     后训练        │
              │ SFT / RL / DPO    │
              │ GRPO / RLVR 等    │
              └─────────┬─────────┘
                        │
              ┌─────────┴─────────┐
              │     预训练        │
              │ 数据 / 分词器      │
              │ 分布式训练        │
              └─────────┬─────────┘
                        │
              ┌─────────┴─────────┐
              │     推理          │
              │ vLLM / 内核       │
              │ 量化              │
              │ KV 缓存 / MoE     │
              └─────────┬─────────┘
                        │
              ┌─────────┴─────────┐
              │ GPU / CUDA        │
              │ CUDA 内核         │
              │ NCCL / PCIe       │

              ┌─────────┴─────────┐
              │ 硬件 / 系统       │
              │ GPU / HBM / NIC   │
```

有趣的是：**越往底层，人才池越小。**

能够掌握以下技能的人：

```text
PyTorch
   ↓
分布式训练
   ↓
CUDA
   ↓
GPU 内存
   ↓
NCCL
   ↓
内核优化
   ↓
实际硬件行为
```

比只会调用大语言模型 API 的人要稀缺得多。

### 预训练工程师

对理解以下内容的人才会有需求：

```python
loss = cross_entropy(model(tokens), targets)

loss.backward()

# 然后理解实际发生的过程：
GPU
 ↓
矩阵乘法
 ↓
Tensor Core
 ↓
HBM
 ↓
NCCL
 ↓
另一个 GPU
```

在规模化层面，问题会变成：

* FSDP / ZeRO
* 张量并行
* 流水线并行
* 专家并行
* MoE 路由
* FP8 / FP4
* 检查点
* 数据管道
* 优化器内存
* GPU 利用率
* 通信/计算重叠
* 容错

这与“微调模型”是完全不同的工作。

### 后训练可能会增长得更快

随着基础模型变得商品化，公司需要让它们 **对特定目标有用**。

例如：

```text
基础模型
    ↓
SFT
    ↓
偏好优化
    ↓
RL
    ↓
可验证奖励
    ↓
工具使用
    ↓
推理
    ↓
智能体行为
```

因此你会看到这样的职位：

* 后训练工程师
* RL 工程师
* RLVR 工程师
* 推理模型工程师
* 数据/轨迹工程师
* 对齐工程师
* 评估工程师

有趣的是，后训练越来越像 **实验工程**：

```text
假设
   ↓
数据集 / 奖励设计
   ↓
训练运行
   ↓
评估
   ↓
分析失败
   ↓
调整方案
   ↓
再次运行
```

### CUDA/GPU 工程师尤其有价值

这可能是我认为你需要注意的部分。

例如，假设一个模型理论上能达到：

```text
100 TFLOPS
```

但实际工作负载只能达到：

```text
38 TFLOPS
```

能够调查以下内容的工程师：

```text
Python
 ↓
PyTorch
 ↓
Inductor
 ↓
Triton
 ↓
CUDA 内核
 ↓
SM 占用率
 ↓
寄存器压力
 ↓
L2
 ↓
HBM
```

会非常宝贵。

同样，对于推理：

```text
请求
  ↓
调度器
  ↓
预填充
  ↓
注意力
  ↓
KV 缓存
  ↓
解码
  ↓
GPU 内存
  ↓
PCIe / NVLink
```

在大型推理集群中，10–30% 的改进可以带来巨大的经济效益。

## 重要的职业区分

我不认为应该这样想：

> “我需要成为一名大语言模型开发者。”

而是：

> **“我想成为一名理解整个技术栈的 AI 系统工程师。”**

类似于：

```text
                 大语言模型
                  │
        ┌─────────┴─────────┐
        │                   │
     训练                推理
        │                   │
   PyTorch              vLLM
        │                   │
   分布式               CUDA
        │                   │
     NCCL                GPU
        │                   │
       GPU ─────────────── GPU
```

这种技能组合更难被商品化。

而你目前的兴趣点——**训练小模型、vLLM/nano-vLLM、KV 缓存、CUDA、GPU 硬件、多 GPU、内存/PCIe，以及最终的内核优化**——自然地指向了这个方向。

你不必在“大语言模型”和“CUDA”之间做出选择。**最强大的工程师将理解它们交汇之处。**

我还可以为你绘制一份 **2026→2030 AI 系统工程师技能树**——从 CUDA 基础 → Triton → 分布式训练 → 预训练 → 后训练 → 推理，并在每个层级附带具体项目。
