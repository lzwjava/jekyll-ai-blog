问题：TCP 窗口大小有什么作用？

答案：

**TCP 窗口大小控制的是发送端允许一次性“在途”的、尚未确认的数据量。**

可以将 TCP 想象成这样：

```text
发送端                             接收端
  |                                        |
  |---- 数据包 1 ------------------------->|
  |---- 数据包 2 ------------------------->|
  |---- 数据包 3 ------------------------->|
  |---- 数据包 4 ------------------------->|
  |                                        |
  |<--- ACK: 已收到 1-4, 窗口=8 ----------|
```

如果接收端通告：

```text
窗口 = 8 KB
```

那么发送端在必须等待 ACK 之前，大约可以有 **8 KB 的数据未完成**。

### 1. 为什么需要窗口？

如果没有窗口，TCP 实际上会这样做：

```text
发送 1 个数据包
等待 ACK
发送 1 个数据包
等待 ACK
...
```

在高延迟网络上，这将是可怕的。

假设：

```text
RTT = 100 毫秒
数据包 = 1 KB
```

你大约只能获得：

```text
1 KB / 0.1 秒 = 10 KB/s
```

而使用 1 MB 的 TCP 窗口：

```text
1 MB / 0.1 秒 ≈ 10 MB/s
```

因此，窗口允许 TCP **流水线化** 处理许多数据包。

---

### 2. 重要的等式

一个有用的近似值是：

```text
吞吐量 ≈ TCP 窗口 / RTT
```

更精确地说，要充分利用一条链路：

```text
窗口 >= 带宽 × RTT
```

这被称为**带宽延迟积（BDP）**。

示例：

```text
带宽 = 1 Gbit/s
RTT   = 100 毫秒

BDP = 1 Gbit/s × 0.1 秒
    = 100 Mbit
    = 12.5 MB
```

因此，要完全填满一条 1 Gbit/s 的链路，你需要大约 **12.5 MB 的在途数据**。

如果你的 TCP 窗口只有 64 KB：

```text
64 KB / 100 毫秒 ≈ 640 KB/s
```

你将严重地未充分利用这条 1 Gbit/s 的连接。

---

### 3. TCP 实际上有两个重要的窗口

这就是 TCP 变得有趣的地方。

#### 接收窗口 —— `rwnd`

接收端告诉发送端：

> “我有这么多可用的缓存空间。”

例如：

```text
ACK
窗口 = 64 KB
```

这是**流量控制**。

它防止了：

```text
快速的发送端
    ↓
慢速的接收端
    ↓
接收端缓存溢出
```

#### 拥塞窗口 —— `cwnd`

发送端维护另一个限制：

> “基于网络状况，我认为我可以安全地发送这么多在途数据。”

这是**拥塞控制**。

因此，发送端大致受限于：

```text
send_window = min(rwnd, cwnd)
```

这是 TCP 中最重要的概念之一。

```text
                    TCP 发送端
                       |
             +---------+---------+
             |                   |
          rwnd 限制           cwnd 限制
        接收端容量           网络容量
             |                   |
             +---------+---------+
                       |
                 min(rwnd,cwnd)
                       |
                  在途数据量
```

---

### 4. 示例

假设：

```text
rwnd = 1 MB
cwnd = 200 KB
```

那么：

```text
最大未完成数据量 = min(1 MB, 200 KB)
                     = 200 KB
```

接收端可以接受 1 MB，但 TCP 的拥塞控制算法只允许 200 KB 在途。

稍后：

```text
rwnd = 100 KB
cwnd = 500 KB
```

现在：

```text
最大未完成数据量 = 100 KB
```

网络可以处理更多，但接收端没有足够的缓存。

---

### 5. 滑动窗口

随着 ACK 的到达，窗口**向前移动**。

想象一下：

```text
序列号：

0       10      20      30      40      50
|-------|-------|-------|-------|-------|

[====== 窗口 ======]
        ↑
    未确认数据
```

在接收端确认了前 10 个字节后：

```text
0       10      20      30      40      50
|-------|-------|-------|-------|-------|

        [====== 窗口 ======]
```

窗口**向前滑动**。

这就是 TCP 通常被称为**滑动窗口协议**的原因。

---

### 6. 窗口缩放

传统 TCP 有一个 16 位的通告窗口：

```text
最大值 = 65,535 字节
```

这对于现代高速/高延迟网络来说太小了。

TCP 窗口缩放扩展了它：

```text
实际窗口 = 通告窗口 × 2^缩放因子
```

例如：

```text
通告窗口 = 65,535
缩放因子  = 7

窗口 ≈ 65,535 × 128
       ≈ 8 MB
```

缩放因子在 TCP 握手期间协商。

### 我保留的心智模型

TCP 有两个独立的问题：

```text
接收端：
“我还能接收多少数据？”
             ↓
            rwnd

网络：
“我可以安全地发送多少数据？”
             ↓
            cwnd

             ↓

发送端最多可以有：

        min(rwnd, cwnd)

字节的在途数据
```

而关键的性能关系是：

```text
             窗口
吞吐量 ≈ -------
              RTT
```

因此，**TCP 窗口大小从根本上讲是控制 ACK 到达之前可以未完成的数据量**，这使得 TCP 能够有效利用具有显著 RTT 的网络。
