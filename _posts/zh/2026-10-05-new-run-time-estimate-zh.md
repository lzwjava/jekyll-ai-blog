以下是基于观察到的运行数据的计算：

**基线（旧运行，`device-batch-size=2`）**

- 每步耗时：**58.1s**（1143分钟 ÷ 步骤1188 ✓，eta计算正确）
- 3,712步 × 58.1s = **~60h** 纯训练
- 加上约16次val-evals（每250步一次，每次41.9M tokens约10-15分钟），2次CORE evals，约5分钟编译 → **总计~65-67h（约2.8天）**

**新运行（`device-batch-size=1`）**

| 组件 | 估计 |
| --- | --- |
| 每步时间 | 58.1s → **~65-67s**（相同FLOPs，但1024个微步尺寸减半——GEMMs效率略低，每步开销翻倍；慢了约12-15%） |
| 训练，3,712步 | **~67-69h** |
| 验证评估×16 | 每次现在耗时约2倍（评估批次也减半）→ **总计~6-9h** |
| CORE eval ×2（max-per-task=50） | 现在很快，合计**<30分钟** |
| torch.compile warmup | **~5分钟** |

**总计：~75-80h ≈ 3.1-3.3天**（之前约2.8天——你用VRAM余量换取了额外~10-15%的时间，主要花在更慢的步数和评估上）

**里程碑：**

- 步骤250（第一个checkpoint落地）：启动后约**4.5-5h**
- 步骤2000（导致旧运行崩溃的那个点）：运行约**1.9天**——这是检验OOM修复的关键时刻
- 完成：**约3.2天**

一个后来可以回补时间的方法：`--eval-tokens=2097156` 可以把那16次val-evals从约6-9小时削减到总共约1小时（bpb曲线只会略微变噪）。不过一开始不需要。
