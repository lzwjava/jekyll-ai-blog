Let me be upfront first: **MODS is an internal NVIDIA tool, never publicly documented.** The exact flag list differs between MODS versions (367 / 400 / 455 builds), and most "documentation" in circulation comes from the GPU repair community. So below is a practical reference of the flags actually used in repair work — plus how to dump the full list yourself from the binaries you have.

## 1. Get the real help from your own binaries (most reliable)

```bash
# From the shell (before mods loads):
./mods -h                # or --help / -help, varies by version
./mats -h

# After MODS loads (you get a "mods>" prompt):
help                     # lists available JS console commands
help -all                # more detail in some versions
./help.js                # some builds ship a help script
```

The `-h` output is generated by the exact binary you're running — that's the authoritative list for your version. If you run it on your image and paste the output here, I can translate/explain every flag.

## 2. Known MODS startup flags

```bash
./mods [flags] script.js [script args]
```

| Flag | Meaning |
| --- | --- |
| `-skip_rm_state_init` | Skip full Resource Manager initialization — access the GPU at raw hardware level (essential for faulty cards, as explained before) |
| `-notest` | Load MODS and stay resident, don't run any test script |
| `-d N` | Debug/verbose level (higher = more logging, e.g. `-d 5`) |
| `-verbose` | Verbose output (equivalent-ish to raising debug level) |
| `-gpuid N` / `-gpu N` | Target a specific GPU when multiple are present |
| `-sysrm` | Use the system driver's RM instead of MODS-internal RM (rarely useful for repair) |
| `-sim` | Simulation/emulation mode (chip bring-up environments; useless on real cards) |
| `-noinit` / `-skip_dev_init` | Skip device initialization entirely (some builds) |
| `-trace` / `-tracefile x` | Dump internal traces for debugging |

⚠️ Not all of these exist in every build — older 367 builds have fewer.

## 3. Known `gputest.js` arguments (the script, not mods itself)

```bash
./mods gputest.js -skip_rm_state_init -notest
./mods gputest.js -skip_rm_state_init -mfg -notest        # 367 builds
./mods gputest.js -skip_rm_state_init -short -notest      # 400 builds
./mods gputest.js -skip_rm_state_init -oqa -test 118 -matsinfo
```

| Argument | Meaning |
| --- | --- |
| `-mfg` | Run the "manufacturing" test flow — the quick factory-line self-test (367-era builds) |
| `-short` | Short test suite — quick pass/fail screen instead of full suite (400-era builds) |
| `-notest` | Don't run tests, just set up the environment |
| `-oqa` | Output/QA mode — report results in the QA format |
| `-test N` | Run a specific test number (e.g. **test 118 = matsinfo**, the VRAM/module info test used to confirm whether the failure is memory vs. core) |
| `-matsinfo` | Generate MATS-style info output (pairs with `-test 118`) |

The `-test N` numbers are the most interesting part — different N values run different subtests (memory, display, PCIe, clock domains...). Test 118 is the one the manual uses to distinguish core failure from VRAM failure.

## 4. Known MATS flags

```bash
./mats -e 10          # single visible GPU
./mats -n 1 -e 10     # target 2nd GPU (dGPU when iGPU is #0)
./mats -3d_card -e 10 # force 3D-class device path
```

| Flag | Meaning |
| --- | --- |
| `-e N` | **Extent** — test N MB of framebuffer. `-e 10` = 10MB quick scan; bigger number = deeper, slower test |
| `-n N` | **Device index** — which GPU to test (0 = first enumerated, usually iGPU) |
| `-3d_card` | Initialize as 3D/graphics-class device instead of compute — needed by some flows |
| `-auto` | Auto-run without interaction (some builds) |
| `-maxerrors N` | Stop after N errors instead of scanning everything |
| `-pattern X` | Force a specific memory write pattern (some builds) |
| `-help` | Dump this build's actual flag list |

## 5. Inside the `mods>` prompt — useful console commands

Once MODS is loaded (even with `-notest`), you're in an interactive JS shell. Commonly used commands:

```
help                  # list commands
test 118              # run test 118 directly
run gputest.js        # load a script later
dev.list()            # list detected GPUs        (name varies by build)
board                 # show board info
exit / quit           # leave mods
```

(Exact method names vary by build — `help` is your friend here.)

## 6. The practical repair toolkit — the 4 commands that matter

For real-world repair, 90% of the work is just these:

```bash
# ① Environment (must see PASS, otherwise card is unreachable)
./mods gputest.js -skip_rm_state_init -notest

# ② VRAM test on the dGPU
./mats -n 1 -e 10
less report.txt

# ③ Distinguish core vs VRAM failure
./mods gputest.js -oqa -test 118 -matsinfo

# ④ Power-off / reboot
reboot / poweroff
```
